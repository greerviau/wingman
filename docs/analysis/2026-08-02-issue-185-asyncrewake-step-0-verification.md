That earlier document's own "one new fact for the pilot's decision" section is what surfaced `asyncRewake` as the mechanism this plan is built on; this document verifies `asyncRewake` itself, empirically, against the seven open questions the plan's own "What remains unconfirmed" section lists.

Claude Code version at verification time: `2.1.220`, matching the version the plan was written against.

## Methodology: reproducing the pilot's real deployment shape without touching it

The plan's own Step 0 item 1 requires testing "in the pilot's real deployment shape... not a hand-driven scratch session" - specifically the pilot's actual tmux/systemd shape, since the prior dead plan's own failure was environment-sensitive. Testing this literally against the live pilot session (`wingman-main`, the actual running orchestrator) was correctly refused as a target: it would require editing a shared, live production config file the pilot's real session reads from, with no way to independently guarantee a genuine idle/no-keystroke window.

The methodology actually used, confirmed safe and faithful in two steps:

1. **`wingman.service`'s own `ExecStart`** is exactly `systemd-run --user --scope --collect --quiet -- tmux new-session -d -s wingman-main -n wingman "bin/wingman ..."` - a `--user --scope` wrapper around a `tmux new-session`, nothing more exotic. The cgroup/reparenting semantics the dead plan's own Step 0 found (a `&`-backgrounded child reparenting away from its hook process on exit) come from this wrapper shape, not from the session's name or from it being the pilot's own session specifically.
2. **This host's tmux server (pid `540985`) already wraps every pane it spawns - any session, any window - in its own dedicated, automatically-created `systemd --user --scope` unit** (`tmux-spawn-<uuid>.scope`, one per pane, confirmed via `systemctl --user list-units --type=scope`), independent of how that pane's session was created. This is tmux's own systemd integration (this distribution's tmux 3.6 build), not anything wingman-specific. Confirmed directly: `wingman-main`'s own top-level pane (pid `829358`) has exactly this kind of scope (`tmux-spawn-c0da9ffe-...scope`), and so did every throwaway test session created for this verification, with no special invocation needed on this verification's own part to get it - creating a plain `tmux new-session` on this same shared tmux server was sufficient.

Consequence: a throwaway test session, launched as `claude` directly (not `bin/wingman`, which forces `cd` into the main checkout) with its cwd set to this effort's own isolated git worktree, and a throwaway `.claude/settings.json` in that worktree (never the main checkout - worktree trust is inherited from the parent repo per `bin/spawn-crew`'s own "a git worktree carved out of an already-trusted repo needs no separate check" comment, confirmed empirically: no trust dialog, no Bypass-Permissions dialog, appeared in any test session below), reproduces the exact `systemd --user --scope` / tmux-pane wrapping shape the pilot's own session runs under - without touching the pilot's session, its config, or its state at all.

Three throwaway test sessions were used, each a fresh `claude --permission-mode bypassPermissions` process in its own tmux window on the shared tmux server, each independently confirmed to have its own `tmux-spawn-<uuid>.scope`:

- **Session 1** (items 1, 3, 5, 6, 7): three Stop hook entries - a plain synchronous script recording `stop_hook_active` verbatim from stdin on every invocation; an `asyncRewake: true` script sleeping 5s then emitting a distinctive marker and exiting 2, up to 12 iterations; an `asyncRewake: true` script sleeping 60s doing nothing (for the cross-hook scope check).
- **Session 2** (item 4): one `asyncRewake: true, "timeout": 8` entry that traps `TERM`/`INT`, forks a `sleep 120` child, and logs whatever it receives.
- **Session 3** (item 2): one `asyncRewake: true, "timeout": 900` entry sleeping 950s, to confirm an explicit override actually extends the async lifetime past the documented 600s default.

## Findings, against the plan's seven open questions

**1. Does an `asyncRewake` exit-2 rewake actually rouse a genuinely idle session, with no keystroke? CONFIRMED - yes.**
A single prompt ("Reply with exactly the word ACK...") was sent once. The interactive turn ended immediately (`ACK` printed, "Cooked for 2s") while the async hook was still sleeping its full 5s - the stop was genuinely *permitted*, not blocked, confirming the turn was never waiting on the hook. ~5s later, with **no further keystroke into the pane**, a new model turn appeared automatically, reading and responding to the distinctive marker text. This repeated cleanly across 12 consecutive rewakes with no further input at any point. The body arrived exactly via the designed channel: the distinctive text on the hook's stderr, plus `{"decision":"block","reason":...}` as a JSON line on stdout - confirmed by inspecting the actual synchronous sibling hook's own recorded stdin JSON, which showed `last_assistant_message` responding directly to the injected reason text.

**2. Can an explicit `timeout` field raise the async lifetime past the documented 10-minute default, and to what ceiling? CONFIRMED - yes, and precisely.**
Two data points, both exact to the millisecond: `"timeout": 8` killed the hook process at `8.008s` (session 2); `"timeout": 900` killed it at `900.011s` (session 3) - both measured from the hook's own recorded start timestamp to its own recorded receipt of `SIGTERM`. The field is honored linearly and precisely in both directions (shorter than, and far longer than, the documented default), with no sign of a separate hidden ceiling below either configured value. This directly licenses `$WM_STOP_CONTINUITY_WINDOW` (default 480s) staying safely under the settings `timeout: 600` the plan specifies - both are comfortably inside the range now empirically confirmed adjustable.

**3. Does `stop_hook_active` from an in-flight async instance of one hook affect a separate hook's own invocation for the same Stop event? Informative only - not load-bearing (see finding 7 below); partially observed.**
The synchronous sibling hook recorded `stop_hook_active: false` on the very first (non-blocked) Stop event, and `true` on every subsequent Stop event that followed a genuine block from the *other* async hook - consistent with `stop_hook_active` reflecting "did some hook actually block the immediately preceding Stop," not "is some unrelated async hook merely still sleeping." This matches the plan's own design decision to not depend on this signal at all (see finding 7 and the plan's "Why `stop_hook_active` cannot be the recursion guard" section) - `hooks/stop-continuity.sh`'s actual recursion guard is the self-owned, time-bounded in-flight marker, verified directly by this implementation's own test suite, not by this Step 0 pass.

**4. What does the harness do to the hook process and its already-spawned children at timeout? CONFIRMED - a genuinely trappable signal, not an immediate untrappable kill.**
Session 2's hook (foregrounding a `sleep 120` child, `"timeout": 8`) received a **trappable `SIGTERM`** at exactly its configured timeout, giving its own `trap ... TERM` handler the chance to run and forward the kill to its child - which then died, confirmed absent from `ps` afterward. The interactive session itself was completely unaffected (the same turn's `ACK` reply and subsequent idle state were untouched by the hook's own later timeout-kill). This directly confirms the referee/trap design's own assumption: `hooks/stop-continuity.sh`'s `trap 'kill -TERM "$child" "$referee" 2>/dev/null' TERM INT` will actually receive a signal it can act on, not be bypassed by an untrappable kill landing on the hook process itself.

**5. Does an `asyncRewake` exit-2 count against the documented 8-consecutive-block Stop-hook cap? No sign of it applying, through 12 consecutive rewakes.**
Session 1's distinctive-wake hook was driven through 12 consecutive exit-2 rewakes, each identical in shape (5s sleep, distinctive marker, exit 2) - iterations 9 through 12 behaved indistinguishably from iterations 1 through 8, with no throttling, no cap message, and no change in cadence. This test was stopped at iteration 12 (not run further) once an apparent external observer sent an unattended `stop the loop` message into the test session's pane (no tmux client was attached at the time - `tmux list-clients` returned empty - consistent with another process on this same shared tmux server, plausibly a supervising session, noticing the unfamiliar repeating pane output and intervening non-interactively, the same `tmux send-keys`-without-attaching mechanism this verification itself used to drive the test). The test session was killed immediately in response, with the data already in hand. Twelve clean iterations with zero sign of the cap engaging is treated here as sufficient evidence that this design's own heartbeat chain is **not** materially bounded by the block-cap concern the plan's Open Question was worried about - the plan's own recommended default ("ship it") for that question is adopted without needing to escalate it further.

**6. Does `asyncRewake: true` alone suffice, or must `async: true` also be set? CONFIRMED - `asyncRewake: true` alone is sufficient.**
Every test session set only `"asyncRewake": true` (matching the cited `security-guidance` plugin's own usage) and every one produced a working async rewake. No test exercised `async: true` at all, and none was needed.

**7. Does an `asyncRewake` exit-2 rewake set `stop_hook_active: true` on the Stop event that ends the rewoken turn? CONFIRMED - yes.**
The synchronous sibling hook's own recorded stdin JSON showed `"stop_hook_active": false` on the Stop event ending the original (non-rewoken) turn, and `"stop_hook_active": true` on the Stop events ending every subsequent rewoken turn. As the plan itself notes, this is no longer load-bearing for `hooks/stop-continuity.sh`'s own correctness (its recursion guard is the self-owned in-flight marker, not this signal) - it is confirmed here only to settle `hooks/stop-guard.sh`'s own unmodified pass-1/pass-2 expectation on a continuity-triggered Stop event, which this finding satisfies: a continuity rewake's ending Stop event is handled by `stop-guard.sh`'s existing pass-2 branch (mark scratch handled, exit 0 unconditionally) exactly like any other blocked-then-continued turn.

## Conclusion

**Step 0 confirms.** All seven open questions are answered, none unfavorably. Item 1 (the hard gate) is unambiguously confirmed: an `asyncRewake` exit-2 rewakes a genuinely idle Claude Code session with zero keystrokes, via the documented stderr-plus-stdout-JSON channel, under the exact `systemd --user --scope`/tmux-pane wrapping shape the pilot's real deployment uses. Implementation proceeds as designed in the plan, with no changes to the plan's own concrete defaults (`WM_STOP_CONTINUITY_WINDOW=480`, settings `timeout: 600`) - both are now empirically confirmed to sit safely inside the harness's actual adjustable range, not merely assumed to.
