# Half A live verification: `wm_harness_process_identity` and the four #383 audit defects

Date: 2026-08-19

Implements steps 1-5 of `docs/analysis/2026-08-18-remove-bin-wingman-launcher-spec.md`'s migration plan (§8, "Half A"). Grounded against the checkout current when this doc was written.

## §7 risk 1: process-ancestry hop counts, live-verified per harness

The spec's own pseudocode for `wm_harness_process_identity()` (§4.3) called for live verification against all five harness CLIs before shipping, not an assumed hop count. Each of the five was actually run, and a real bash-tool-call ancestor process was inspected via a diagnostic script capturing the full `pid/ppid/comm/args` chain from itself up to `systemd`.

Credentials on this machine cover only claude and opencode (opencode ships a free default model needing none) for a live end-to-end model turn. codex, grok, and pi were exercised through a minimal local mock OpenAI/Anthropic-compatible backend (`/v1/chat/completions` for grok, `/v1/responses` for codex, a custom `openai-completions` provider entry for pi) that inspects the harness's own `tools` schema and returns a real tool call invoking the diagnostic script — a genuine tool-call round trip through each CLI's own real code, not a stub of the mechanism being tested.

| Harness | Hops to match | Ancestor shape found |
|---|---|---|
| claude | 2 | self → `sh -c <command>` (Claude Code wraps every hook command string in a shell, confirmed even for a bare script path with no shell metacharacters) → `claude` |
| codex | 1 | self → `codex` (the vendored Rust binary) directly; its own `codex.js` launch shim, a further `node` ancestor above that, is never reached |
| grok | 2 | self → grok's own sandboxed `bash -O extglob -c ...` command wrapper (comm `bash`, not a match) → `grok` (the vendored binary); its own node trampoline is likewise never reached |
| opencode | 1 | self → `opencode` directly, a real compiled executable, no wrapper |
| pi | 1 | self → `pi` directly — pi's own Bash tool (`dist/core/tools/bash.js`) calls Node's `spawn()` with an argv array, never `shell: true`/a string command, so there is no wrapper shell to begin with; confirmed by reading the shipped source, not assumed |

All five resolve within 1-2 hops. The bound (`WM_HARNESS_WALK_MAX`, default 5) exists specifically because the claude/grok cases show a *shell* wrapper can appear at all — a compound or piped real-world command could add another hop by defeating that shell's own tail-call exec optimization (observed directly: Claude Code's `sh -c` persisted as its own live process rather than collapsing, for reasons independent of command shape) — so the walk checks a bound rather than assuming any one fixed depth. An initial, unmeasured default of 12 caused a genuine CI regression: the no-match case (no `WINGMAN_RUN_ID`, no recognizable harness ancestor - the shape any CI runner has) always walks the full bound, and the added `ps`-fork latency on `bin/watch-fleet`'s own re-arm path made a timing-sensitive test (`tests/stop-continuity-pr-watch.test.sh`) fail intermittently in CI specifically - reproduced locally by forcing the same no-match shape. Tightening to 5 was NOT, on its own, what fixed it — see "Correction (review round 2)" below for what the actual root cause turned out to be, and for the one live consumer that needed more than 5 hops.

`comm` is what `ps -o comm=` reports, which reflects the *executed file's own basename* — confirmed live that this is unaffected by `argv[0]` (`exec -a NAME cmd` does not change it) and, for a shebang script, shows the *interpreter's* basename, not the script's. This is why codex/opencode/grok surface their own compiled-binary names directly while a bash wrapper always surfaces as `bash`.

**What this proves, and what it does not.** The five installs on this machine all resolve, and codex/grok/opencode are real compiled binaries (their own name is unavoidably their own `comm`), while pi is a Node entry point that explicitly sets `process.title` (`dist/cli.js`) — none of the five ships as a bare shebang shim with no name of its own. Recognition by `comm` is a property of *these installs*, not a property the mechanism guarantees for any conceivable install of the five: a shebang wrapper that never sets its own process title would surface its interpreter's name (`bash`/`node`) and match nothing. `bin/lib/harness-identity.sh`'s own header documents this constraint, and the walk's own no-match path traces the reason to a log file (`$WINGMAN_HOME/harness-identity.log`) rather than failing silently — see "Correction (review round 2)" below for why a log file, not stderr.

## Step 1: `wm_harness_process_identity()`

Added to `bin/lib/harness-identity.sh`, a new file sourced by `bin/lib/common.sh` (so every existing consumer — `bin/watch-fleet`, `bin/spawn-crew`, `bin/crew-resume` — gets it for free) and sourced directly by the four per-tool-call hooks and `hooks/lib/watcher-liveness.sh`, which deliberately avoid `common.sh` itself (its `config.local.toml` load is a real `uv run` subprocess on any machine that has one, unacceptable on a per-tool-call hot path). Every sourcing site tolerates the file being absent (a partial/broken install), degrading to "no computed identity" rather than a raw shell error.

## Steps 2-4: every consumer of `$WINGMAN_RUN_ID`

`hooks/pilot-preferences-guard.sh`, `hooks/pilot-preferences-nudge.sh`, `hooks/artifact-link-guard.sh`, `hooks/pr-open-marker-tracker.sh`, `bin/watch-fleet`'s `$RUNFILE`/`$SUPPRESSEDFILE` stamps, `hooks/lib/watcher-liveness.sh`'s `wm_run_scoped_stamp_active`/`wm_run_scoped_marker_active`, and `bin/spawn-crew`/`bin/crew-resume`'s exported `WINGMAN_RUN_ID` line now all resolve `$WINGMAN_RUN_ID` when genuinely exported (a settable override — existing test fixtures depend on setting it directly), else `wm_harness_process_identity()`.

Two more consumers, found by review rather than in the original audit, needed the identical substitution to close the loop: `hooks/stop-continuity.sh`'s five stamp-writing sites (`$inflightfile`/`$stopfile`/`$killstampfile`) were still writing the bare `${WINGMAN_RUN_ID:-}` even after `hooks/lib/watcher-liveness.sh`'s *read* side was migrated — on the no-launcher path every stamp was therefore always written empty, which made the predicate's own "either side empty, honor it" fallback fire unconditionally, so the marker-scoping fix was inert in practice for stop-continuity's own files specifically (the reader logic was correct, but no real writer on that path could ever produce a stamp for it to correctly reject). And `hooks/lib/guard_policy.py`'s `no_foreground_watcher_guard` (shared by claude's own `hooks/no-foreground-watcher-guard.sh` and the four non-claude dialects via `guard_dispatch.py`) read the bare `WINGMAN_RUN_ID` against `$SUPPRESSEDFILE`, which `bin/watch-fleet` now stamps with the computed identity — the two newly disagreed, so a stale standdown from an ended run could wrongly deny a legitimate arm in a new one.

`guard_policy.py` gained its own `_wm_effective_run_id()`. Its fallback shells out to `wm_harness_process_identity` when nothing has resolved yet, but that fallback is not what actually runs in production: called from where `evaluate_no_foreground_watcher_guard` sits inside `guard_policy.py`'s own nested `python3`/`uv`/command-substitution call chain, the shell-out measured live at 6 hops from the harness — one more than `WM_HARNESS_WALK_MAX`'s bound (5) allows (see "Correction (review round 2)" below). Rather than raise the bound to cover one deep caller at the cost of the no-match/CI-runner latency for every other one, the two entry points that actually reach this guard — `hooks/no-foreground-watcher-guard.sh` (claude) and `hooks/lib/guard_dispatch.py` (the other four dialects) — resolve the identity themselves at their own shallow depth (2 hops, the same claude/grok case already in the hop-count table above) and export/set `WM_EFFECTIVE_RUN_ID` before `guard_policy.py` ever runs. `_wm_effective_run_id()` checks for that pre-resolved value first and only reaches its own deep shell-out for a caller that invokes the guard directly, bypassing both entry points — not a shape either dispatcher takes today.

One correctness point beyond a mechanical substitution: `hooks/pilot-preferences-guard.sh`/`-nudge.sh` used to tell the model it could type the bare `"$WINGMAN_RUN_ID"` shell-variable reference as a shorthand for the escape-hatch command. That shorthand is now offered only when the value is genuinely exported — a computed identity was never exported into the model's own shell, so instructing it to type that reference would resolve to empty there and cache the answer under the wrong key. The primary escape-hatch form (which always embeds the resolved value literally) is unaffected either way.

Two prose consumers also assumed an unset `$WINGMAN_RUN_ID` meant "nothing to do", now stale: `.claude/commands/prefs.md`'s step 1 said to no-op when unset — now false, since the preferences guard gates even without one, which would otherwise make `/prefs` silently no-op while every tool call is denied. `bin/config`'s onboarding-preferences diagnostic said "not launched via bin/wingman, so no run-scoped answers" for the same unset case — now resolves and displays the computed identity's own answers instead.

`.claude/commands/prefs.md`'s own resolution went through two shapes (see "Correction (review round 2)" below for why). It now resolves the run id as its own separate Bash call — `bin/lib/harness-identity.sh` (made directly executable, not only sourceable, for exactly this caller) or `$WINGMAN_BIN/lib/harness-identity.sh` — and reuses that captured value literally everywhere `--run-id` appears in the rest of the recipe, rather than embedding the resolution as a compound subshell inside the same command line as the `wm-state.py` calls the file's `allowed-tools` frontmatter pre-approves.

## Step 5: the four audit defects, reproduced and confirmed fixed

Each row of the spec's own §2 audit table now has a real regression test, added to the existing test suite, that reproduces the exact defect shape via a deterministic fake harness ancestor (`wm_fake_harness_bin`, `tests/lib.sh` — a byte copy of `bash` under a literal `claude`/`codex`/etc. filename, since `ps -o comm=` tracks the executed file's own basename, not `argv[0]` or `exec -a`) rather than depending on whatever real process happens to be running the test suite.

- **`hooks/pilot-preferences-guard.sh` (the audit's "most severe finding")** — `tests/pilot-preferences-guard.test.sh`. Before: no `WINGMAN_RUN_ID` exported → the guard reports `[]` (silent no-op) for every tool call. After: run through a fake `claude` ancestor with no `WINGMAN_RUN_ID` exported, the guard now denies and names a real, non-empty computed run id in its escape hatch.
- **`hooks/artifact-link-guard.sh`** — `tests/artifact-link-guard.test.sh`. Before: `artifact_linking=artifact` cached under a real run id, but no `WINGMAN_RUN_ID` exported at report time → silent allow (`[]`), the publish requirement never checked. After: `artifact_linking=artifact` is cached under the *exact identity the guard will independently compute* (pre-seeded by a helper process sharing the same fake-claude ancestor), and the guard — run with no `WINGMAN_RUN_ID` exported — now denies, naming the deliverable.
- **`bin/watch-fleet` foreign-cycle takeover** — `tests/watch-fleet-lifecycle.test.sh`. Before: an old cycle stamped with one run's id, a new arm with no `WINGMAN_RUN_ID` exported → `owner_lock_alive`'s ownership check is unconditionally true, the foreign cycle is silently adopted as healthy. After: the new arm, run through a fake `claude` ancestor with no `WINGMAN_RUN_ID` exported, computes a real identity that differs from the old cycle's literal stamp, correctly detects it as foreign, and replaces it (`Replacing it with a cycle this run tracks`) — never `healthy`.
- **`hooks/lib/watcher-liveness.sh` marker/kill-stamp scoping (`wm_run_scoped_stamp_active`)** — verified directly, AND end to end through its two real writers now that they are fixed too (see above): `hooks/no-foreground-watcher-guard.sh`'s own standdown check (`tests/no-foreground-watcher-guard.test.sh`) proves a standdown marker genuinely stamped under the computed identity by one fake-claude process is correctly read back as active by a guard invocation sharing that same ancestor. A companion case (added in review round 2, after the first version of this case was found not to discriminate the fix from a reverted one) runs the identical fake-ancestor setup but stamps the marker under a rid that is NOT this run's own computed identity, and asserts it is correctly read back as inactive — proving the guard compares the computed identity rather than treating "a marker file exists" as sufficient to deny on its own. `hooks/stop-continuity.sh`'s own five stamp-writing sites had no coverage at all against a real computed identity until review round 2: `tests/stop-continuity.test.sh`'s new case (6e) runs the hook through a fake-claude ancestor and checks both the in-flight marker (written unconditionally near the top of every invocation) and `$killstampfile` (the TERM-path writer) against an independently-computed identity for that same ancestor — all five sites read the one `$WM_EFFECTIVE_RUN_ID` resolved once at source time, so two independent write sites agreeing on the right value covers the shared resolution behind all five.

The one case each defect's fix still legitimately defers to legacy "honor it" behavior — neither side resolves at all (`ps` unavailable, or `WM_HARNESS_WALK_MAX=0`, an explicit test-only override) — is also covered, so the fix is proven to change behavior *only* where the audit found a real gap.

## Constraint on the hop-count verification (review round 1)

"Live-verified against all five supported harness CLIs" is a claim about the five installs actually tested on this machine, not an unconditional property of the mechanism: recognition requires the harness's own process image to carry its own name (see the "What this proves" paragraph above). `bin/lib/harness-identity.sh`'s own header now states this constraint, and a no-match walk traces its reason (`wm_harness_process_identity: reached the top of the process tree ... with no recognized harness ancestor ...`) to `$WINGMAN_HOME/harness-identity.log` instead of returning empty with no trace at all — see "Correction (review round 2)" below for why a log file rather than stderr, where this originally landed.

## Correction (review round 2)

The claim in "§7 risk 1" that tightening `WM_HARNESS_WALK_MAX` from 12 to 5 was "confirmed fixed" was premature — the same CI-mimicking local reproduction still failed at the new default. Root cause: the no-match path's own diagnostic tracing wrote to stderr, and several existing tests (`tests/watch-fleet.test.sh`'s racer cases among them) treat a hook's or `bin/watch-fleet`'s own stdout/stderr as a structured or timing-sensitive channel (e.g. polling "the log file becomes non-empty" as a liveness signal) — a stray diagnostic line landing there broke several of them, independent of the bound's value (confirmed directly: `WM_HARNESS_WALK_MAX=2` still left failures). The trace now writes to a dedicated log file (`$WINGMAN_HOME/harness-identity.log`), never stdout/stderr, and every call site's own `2>/dev/null` guard reverted to the simple form (it only ever needed to guard "command not found", not a diagnostic line).

Separately, 5 remains genuinely insufficient for one caller: `guard_policy.py`'s own fallback shell-out, invoked from inside its own nested `python3`/`uv`/command-substitution chain, measured live at 6 hops. Rather than raise the bound (taxing the no-match/CI-runner latency case for every other caller to cover one), the fix moved the resolution point — see the `guard_policy.py` paragraph above.

Two further items from review round 2, beyond the hop-count claim: `.claude/commands/prefs.md`'s round-1 fix still depended on `$WINGMAN_BIN`, which is unset in exactly the no-launcher scenario the fix targets — rewritten as described above. And the round-1 regression tests for `hooks/no-foreground-watcher-guard.sh`'s standdown check and for `hooks/stop-continuity.sh`'s stamp sites did not actually discriminate the fix from a reverted one (both passed unchanged when the underlying resolution was deliberately broken) — both rewritten and verified, by reverting the corresponding fix and confirming the new assertions fail, to genuinely discriminate (see the Step 5 section above).

One more found by this round's own full-suite re-verification, not by the reviewer: moving the resolution point shallower (the `guard_policy.py` fix above) means `hooks/no-foreground-watcher-guard.sh` now calls `wm_harness_process_identity` from much closer to the process actually running it — including, when the test suite itself is run from inside a real `claude` session (the ordinary way development on this repo happens), a genuine `claude` ancestor within the walk's own bound where the old, deeper call site would not have found one. `tests/owner-paths-cross-derivation.test.sh`'s standdown-marker check assumed no identity would ever resolve in the ambient test environment and stamped its marker with a placeholder (`"x"`) rather than a real computed identity; that assumption silently broke, since the guard could now legitimately resolve a real one that did not match the placeholder. Fixed by forcing `WM_HARNESS_WALK_MAX=0` on that check's own guard invocation, the same pattern `tests/watch-fleet-lifecycle.test.sh` already uses for the identical reason.

## Scope relative to issue #383

This PR is a non-closing reference (`Part of #383`, not `Fixes #383`) on a first reviewer's finding: issue #383's acceptance criteria are attributed by the spec itself to *both* §4.3 (this PR) *and* §4.5's bootstrap routine (Half B, not yet built). Half A fixes the run-id-computation defects the spec's own live audit (§2) found and makes criteria 1's "verified watcher" and 3's wake events correct wherever they were silently broken by an empty run id, plus the missing-metadata slice of criterion 5's test coverage — but it adds no new "visible hard failure" surface, and criteria 2 (validate ownership before treating a spawn as supervised) and 4 (no duplicate cycles from Stop hooks vs. explicit arming) depend on the bootstrap gate that only Half B builds. #383 stays open until Half B lands.
