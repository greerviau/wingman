# A blind `C-c` clear-keystroke aborted a lead's in-flight spawn, and the resulting denial was absorbed into silence

**Date:** 2026-07-30
**Mode:** investigate only (report mode) - no fix applied, no PR opened, no GitHub issue filed.

## Summary

A lead (`own-the-engineering-skills-expan-lead`, effort: engineering-skills expansion in `greerviau/skills`) tried to spawn a reviewer for PR #18. The spawn's `Bash` tool call was denied with harness boilerplate ("The user doesn't want to proceed with this tool use... STOP what you are doing and wait for the user to tell you how to proceed"). The lead then asked a question into its own pane ("How would you like me to proceed with reviewing PR #18?") and waited. It never set `blocked`, so no watcher fired and nothing reached the orchestrator. The mechanical stall detector eventually flipped the lead to `stalled`, with a preserved "last summary" that predated the whole episode and said nothing about a denial or an unanswered question. The requester found the real state only by attaching to the tmux window by hand.

Three findings, not two - a third surfaced live, mid-investigation, directly from the orchestrator's own session, and is folded in here at the requester's instruction:

- **Defect A (root cause of the denial): not a hook, not a permission rule, not a misconfigured guard at all.** The lead's own `bin/spawn-crew --type reviewer ...` `Bash` call was genuinely mid-execution when the *developer* (the PR's own author, reporting its work as ready) called `bin/crew-say` to notify the lead. `crew-say`'s delivery primitive (`bin/lib/common.sh`'s `wm_tmux_send_message`) sends a literal `Ctrl-C` tmux keystroke into the target pane before typing, to clear any stray composed text sitting in the chat input box. That keystroke landed while the lead's `spawn-crew` call was still running, and Claude Code's own harness interpreted it as the user interrupting the current tool call - a real, correctly-functioning interrupt, aimed at the wrong moment. None of the six-plus `PreToolUse` hooks that can deny a crew `Bash` call fired; the transcript evidence (below) rules every one of them out directly, not by inference.
- **Defect B: the playbooks have no general instruction for "a tool call of mine was denied," and the stall detector cannot mechanically distinguish a genuinely crashed/hung session from one sitting responsively on its own unrelayed question.** Both gaps are real and independently worth closing, on top of fixing Defect A.
- **Defect C (reported live by the orchestrator mid-investigation): `bin/watch-fleet` is armed via a bare relative path that depends on the orchestrator's own current working directory**, which can (and did) drift after an earlier `cd` into a crew member's repo, producing a silent, unsupervised fleet until the orchestrator happened to notice the nonzero exit code itself.

All three are detailed below with exact file/line citations and, for Defect A, the live transcript evidence that pins the cause beyond reasonable doubt.

## Defect A: root cause of the spawn denial

### The mechanism is confirmed, not inferred

The lead's transcript (`da4fa688-c7f4-48f9-94ae-2767ac483359.jsonl`) shows this exact sequence:

- **17:29:43.465Z** - the lead's own turn issues a `Bash` tool call: `$WINGMAN_BIN/spawn-crew --type reviewer --repo /home/greer/github/skills --objective "Review PR #18 ..."` (`tool_use` id `toolu_01HfzdR86mnSRpCayR2MTJHK`).
- **17:29:49.000Z** - that tool call's result arrives as a denial:

  ```json
  {"type":"tool_result","content":"The user doesn't want to proceed with this tool use. The tool use was rejected (eg. if it was a file edit, the new_string was NOT written to the file). STOP what you are doing and wait for the user to tell you how to proceed.","is_error":true,"tool_use_id":"toolu_01HfzdR86mnSRpCayR2MTJHK"}
  ```

  with the transcript's own metadata tagging it `"toolDenialKind":"user-rejected"`.
- **17:29:49.002Z** - the next transcript line is literally `{"type":"text","text":"[Request interrupted by user for tool use]"}`.
- **17:29:50.291Z** - a new user turn lands: `"Message from implement-the-mermaid-skill-from-developer: read /home/greer/.wingman/say/own-the-engineering-skills-expan-lead-1785432568-2315533.md and act on it now..."` - the developer's own PR-ready notification to the lead.

`toolDenialKind: "user-rejected"` plus `"[Request interrupted by user for tool use]"` is Claude Code's own code path for a **live interrupt of an in-flight tool call** - functionally identical to a human pressing Ctrl-C mid-command. It is a different code path from a `PreToolUse` hook veto, and this is independently, directly confirmed: a survey of every denial across this crew's own live transcripts in the same project directory turns up two distinct `toolDenialKind` values, `permission-rule` (5 occurrences, real hook denials with the hook's own custom reason text verbatim - e.g. `artifact-link-guard.sh`'s exact "You are reporting a markdown deliverable..." message, and `no-merge-guard.sh`'s exact `PARSE_FAIL_REASON` text) and `user-rejected` (exactly this one occurrence, carrying zero hook-specific text - pure harness boilerplate). No hook fired here. A hook denial and a live interrupt are mechanically distinguishable in this harness, and the evidence is unambiguous about which one this was.

The developer's own transcript (`b3e8d312-a1d4-4f5c-98e1-e85fba9610b3.jsonl`) confirms the colliding action: at **17:29:27.648Z**, it ran `$WINGMAN_BIN/crew-say own-the-engineering-skills-expan-lead "Mermaid skill PR is ready for review: https://github.com/greerviau/skills/pull/18 ... Please spawn a reviewer as my sibling..."` - a wholly legitimate, independently-correct action (the PR's own author reporting readiness to its owner, exactly as `_delivery.md` and the status contract call for).

`bin/crew-say` delivers into a live session via `wm_tmux_send_message` (`bin/crew-say:76`), which is `bin/lib/common.sh`'s shared primitive (also used by `bin/crew-ask`, `bin/crew-resume`, `bin/spawn-crew`'s opening-message delivery, `bin/crew-standdown`, and `bin/watch-fleet`). Its locked implementation, `_wm_tmux_send_message_locked` (`bin/lib/common.sh:653-662`):

```bash
_wm_tmux_send_message_locked() {
  _target="$1"; _text="$2"
  wm_tmux_pane_ready "$_target"
  [ $? -eq 2 ] && return 2
  _sm_clear_keys="${WM_CLEAR_KEYS-C-c}"
  if [ -n "$_sm_clear_keys" ]; then
    wm_tmux send-keys -t "$_target" $_sm_clear_keys
    sleep "${WM_CLEAR_DELAY:-0.3}"
  fi
  wm_tmux send-keys -t "$_target" -l "$_text"
  ...
```

The comment block above it (`bin/lib/common.sh:595-608`) explains the intent precisely: `WM_CLEAR_KEYS` (default `C-c`) is sent once, before typing, to clear any stray unsubmitted text already sitting in the target's chat input box (left over from direct Remote Control interaction or other stray typing) - "verified against a live Claude Code pane, a single Ctrl-C clears the composer's current text without exiting... and a lone Ctrl-C against an already-empty box is a harmless no-op." That claim is true only when the target is genuinely idle at an empty chat prompt. It does not hold when the target's own turn is actively executing a tool call: Ctrl-C delivered mid-execution is not a harmless no-op against an empty box, it is a real interrupt of whatever is running - exactly what the transcript shows.

The gate meant to prevent exactly this, `wm_tmux_pane_ready` (`bin/lib/common.sh:544-561`), only checks two things: whether the pane's captured text is byte-stable across consecutive polls, and whether that stable text is dialog-shaped (a permission/trust prompt). It has no concept of "the target's agent turn is currently running a tool with no new terminal output yet" - a long-running `Bash` call like `spawn-crew` (which does workspace-trust checks, tmux window creation, `wm-state crew-add`, playbook rendering, and message-queue delivery, all without printing anything to the lead's own pane in the meantime) presents identically to a genuinely idle, stable prompt. The function is explicitly bounded and fails open: "a pane that never settles still proceeds rather than hanging (returns 0, same as an ordinary ready pane - there is nothing more specific to report)." There is no signal anywhere in this call path that distinguishes "idle with stray text" from "busy running a tool" - both look byte-stable, and both are treated as safe to clear.

This is precisely reproducible in concept, without needing a live incident: any two crew sessions where session B calls `crew-say`/`crew-ask` (or any `wm_tmux_send_message` caller with the default `WM_CLEAR_KEYS=C-c`) targeting session A, at a moment when session A's own turn is mid-execution of any `Bash` tool call producing no fresh pane output, will reproduce the exact same interrupt. It requires no misbehaving guard, no misconfiguration, and no unusual command shape - it is a race between two independently correct actions, mediated entirely by a keystroke sent blind to the target's execution state.

### What this is *not*

For completeness, per the brief's instruction to enumerate every denial mechanism: this transcript evidence directly rules out all of the following, none of which produced a `permission-rule`-tagged denial at this timestamp, and none of which reference `spawn-crew` in any way that would match this call even in principle:

- `hooks/no-merge-guard.sh` (`PreToolUse`, matcher `Bash`) - its own substring pre-gate (`no-merge-guard.sh:224-228`) requires `merge`/`push`/`allow-merge`/`review-gate`/`crew-add`/`--delivery`/`review-token`/`crew-set...--type` to appear in the command text at all; its `check_crew_add_restriction()` (`:993-1028`) only fires on a literal `wm-state crew-add`/`crew-set` segment in the command, never on `bin/spawn-crew` itself (which the comment explicitly documents as the one legitimate caller of `crew-add`, exempted for a lead spawning a new, non-self worker).
- `hooks/no-direct-edit-guard.sh` (`PreToolUse`, matcher `Edit|Write|NotebookEdit|Bash`) - active unconditionally for `WINGMAN_CREW_TYPE=lead`, but for `Bash` it only denies direct test-runner invocations (`pytest`/`npm test`/`go test`/etc., `no-direct-edit-guard.sh:149-182`); `spawn-crew` matches none of those patterns.
- `hooks/api-outage-spawn-guard.sh` / `hooks/usage-limit-spawn-guard.sh` (`PreToolUse`, matcher `Bash`) - both gate on a fleet-wide state file (`api-outage-state.json` / `usage-limit-state.json`) reading `active`/`approaching`/`paused`; both produce a distinctive custom denial message naming the outage/usage-limit condition and the override flag, which is not what appears here, and (not shown, but checkable) neither state file was in a blocking state at this timestamp.
- `hooks/no-watcher-kill-guard.sh` - only matches `kill`/`pkill`/`tmux kill-*` targeting a live watcher pid; irrelevant to a `spawn-crew` call.
- `hooks/artifact-link-guard.sh` - only matches `wm-state.py crew-set --status review|done`; irrelevant here.
- `hooks/pilot-preferences-guard.sh` - only active while onboarding preferences are unanswered for the run, and even then allows `bin/spawn-crew`... indirectly (it is scoped to wingman's own onboarding, not crew `Bash` calls in general - preferences were already resolved for this run regardless).
- No `permissions.deny` rule exists anywhere in scope: user-level `~/.claude/settings.json` has `"permissions": {}`; the wingman repo's own project `.claude/settings.json` only has an `allow` entry for `bin/crew-standdown`; the `skills` repo (the lead's own project root) has no `.claude/` directory at all.
- Recommendation 3 from issue #212 (a hook mechanically restricting `spawn-crew` to orchestrator-type callers) was **settled but not yet implemented** - no such hook exists in `hooks/` today. It would not have denied this call regardless (a lead spawning a worker is exactly the case that design allows), but it is confirmed absent, not silently assumed absent.

### Blast radius

This is **not scoped to leads, to reviewer spawns, or to any particular guard's misconfiguration.** `wm_tmux_send_message` (and its default `C-c` clear) is the shared delivery primitive behind `bin/crew-say`, `bin/crew-ask`, `bin/crew-resume`'s resume-nudge, `bin/crew-standdown`'s reconnect message, and - critically - `bin/watch-fleet`'s own stall-check nudge (`bin/watch-fleet:1077`) and its `/remote-control` reconnect retry (`:974`, `:924`, `:928`). (`bin/spawn-crew`'s own opening-message delivery, `:509`, and `bin/crew-resume`'s resume-nudge, `:286`, already pass `WM_CLEAR_KEYS=""` to disable the clear-keystroke for those two specific, known-empty-composer cases - so those two are already immune.)

Any crew session (a `lead`, or any worker type) whose own `Bash` tool call happens to be executing without fresh pane output at the exact moment ANY of the following reaches it can have that call aborted the same way: its owner or a sibling calling `crew-say`/`crew-ask`, `watch-fleet`'s own check-in nudge (sent specifically to *test* whether a member is stalled), or a reconnect retype. This is a genuine, general race in the message-delivery layer, present since `wm_tmux_send_message`'s `C-c` clear-key convention was introduced, and it is not gated on crew type, effort, or repo. The `watch-fleet` stall-nudge case is the most concerning instantiation: the nudge exists specifically to distinguish "still working" from "genuinely idle," and as built, it can itself convert genuine, in-progress work into an aborted tool call and an apparent stall - actively working against its own purpose.

## Defect B: a denial became silence

### Does any playbook say what to do when a tool call is denied?

**Only for three narrow, specific cases - there is no general rule.** Checked directly against every playbook and the status contract:

- `playbooks/_status-contract.md:53` ("blocked for a human dependency," case 2) covers exactly `AskUserQuestion`/`EnterPlanMode`/`ExitPlanMode` being mechanically denied (`hooks/no-interactive-prompt-guard.sh`): "If you find yourself needing one of them, that need itself is the signal to report `blocked` instead."
- `playbooks/common/lead.md:76` covers exactly a `spawn-crew` denial during an active API outage/usage-limit pause: "a denied spawn during an active outage is not a decision to escalate, just wait and retry (or use `--force-during-outage`...)."
- `playbooks/_delivery.md:98` covers exactly a merge attempt denied by the review-evidence gate: "report `blocked` naming exactly what's missing."

None of these three is the case that happened here (an unexpected, unrecognized interrupt on an ordinary `spawn-crew` call), and there is no fallback rule anywhere for "a tool call was denied and I don't recognize why." The lead had no documented instruction to follow, so it improvised - and what it improvised (asking a question into its own pane and waiting) is a reasonable-looking response to the denial's own literal text: the harness's generic boilerplate says, verbatim, "STOP what you are doing and wait for the user to tell you how to proceed." That instruction is correct advice for an attended, interactive session where a human is watching the pane in real time - it is actively wrong advice for a crew session, which per the status contract's own case 2 has "no way to sit on a live, interactive human-facing prompt and wait for someone to answer it in real time." The lead did not fail to think; it followed the only instruction visible to it, which happened to be written for the wrong kind of session.

### Is there a natural representation for this in the status contract?

Yes - the shape already exists for a narrower case and generalizes cleanly. Case 2 of "blocked for a human dependency" is structured as: *tool X is denied because no one is watching this pane interactively* -> *that denial is itself the signal to report `blocked`*. The missing piece is simply stating this for *any* tool denial without an already-documented remedy, not inventing a new mechanism.

### Can the stall detector tell "wedged waiting for input" from "genuinely idle"?

**No, and the reason is structural, not a bug in the detector's logic.** `cmd_stall_check` (`bin/lib/wm-state.py:1426-1528`) gates a flip to `stalled` on three things all holding at once: `pane_idle`/`status_idle` past `--threshold`, `_probe_execution` finding no live, CPU-active descendant process under the member's own pane pid, and a prior check-in nudge having already had a full cooldown window. Every one of these signals was, in this incident, **genuinely true** - the lead really was sitting idle, with no running child process, after asking its question and getting no reply. The detector is not misfiring; "idle" is an accurate description of the process/pane state. The problem is that "idle" is overloaded: it is the correct signal for both a crashed/hung session and a live, fully responsive session that is simply parked on its own unrelayed question, and both present identically from outside the pane (no CPU activity, no new output, status stuck at `working`). Disambiguating them requires reading pane *content*, not just pane *activity* - a fundamentally different (and fuzzier) kind of check than anything the stall detector does today, and one this codebase deliberately avoids in general (routine pane-scraping is exactly what CLAUDE.md's prime directive rules out).

The one piece of the mechanism meant to soften this - "the flip preserves your last summary inside the stall reason" (`playbooks/_status-contract.md`, "A state you never set yourself: `stalled`") - is only as good as the member's own last reported summary. Here, the lead never called `crew-set` again after asking its question (there was no tool call left to attempt one from - it just ended its turn on a text response), so the summary frozen into the stall reason was whatever predated the whole PR #18 episode: "no pane output, status update, running child process, or CPU activity for >Ns... (last summary: PR 1 (non-skill fixes) merged by the human. Starti...)" - stale and unrelated to the actual cause, exactly matching the incident's own description ("surfaced as 'stalled' ... with no indication of the real cause").

Building a heuristic pane-content scan (e.g., "does the tail look like the assistant asked a question") to produce a more specific fire reason is possible in principle - the existing dialog-shape detector (`prompt_shape_in`, `bin/lib/common.sh:481-526`) already does something structurally similar for permission dialogs - but a dialog has a rigid, grammar-like shape (numbered options, a selection marker) that a free-text question does not, so this would be materially fuzzier and lower-confidence than the existing detector. It is not recommended as a first move; see ranked recommendations below.

## Defect C: the watcher's own arm command is a relative path

Reported live, mid-investigation, directly by the orchestrator's own session, having just hit this in its own operation: the orchestrator arms its supervision loop by running `bin/watch-fleet` as a harness-tracked background task. This is a bare relative path, so it resolves against the orchestrator's own shell working directory - which persists across the whole session and drifts the moment any earlier command `cd`s elsewhere (the orchestrator gave the concrete example of `cd`-ing into a crew member's repo to run `gh`). When it drifted, the arm exited 127 (command not found), and the fleet was left with no live watcher at all - no wake could reach the orchestrator for any crew event, from any member, until the next time something happened to notice.

This is confirmed as a real, live occurrence (not a hypothetical), and it is a documentation/convention issue, not a missing mechanism, exactly because the mechanism already exists elsewhere in this same codebase and simply isn't used consistently:

- `.claude/settings.json` (the wingman repo's own project settings) already registers every hook via the absolute-anchored form, e.g. `"$CLAUDE_PROJECT_DIR/hooks/stop-guard.sh"` - never a bare relative path.
- Every crew session (a lead or a worker) is launched with `$WINGMAN_BIN` exported (confirmed live via `ps`: `--add-dir /home/greer/github/wingman`, and the session's own env), and `playbooks/common/lead.md:42` explicitly instructs a lead to arm its own cycle via `$WINGMAN_BIN/watch-fleet` - the absolute form. **Leads are already immune to this exact failure**, because their own playbook never uses the bare relative spelling.

The bare relative form survives only in the *orchestrator's* own operating instructions: `CLAUDE.md:98,103` ("`bin/watch-fleet` blocks..."; "Use the raw `Bash` forms instead - `bin/watch-fleet` to arm, `bin/watch-fleet --classify` to process a wake") and `.claude/commands/watch.md` (its own worked examples, and its `allowed-tools: Bash(bin/watch-fleet:*)` frontmatter pattern). The orchestrator has no `$WINGMAN_BIN` of its own to fall back on (it *is* the top-level session; `$WINGMAN_BIN` is a variable crew sessions get, not one the orchestrator's own launch defines) - but it does not need one: `$CLAUDE_PROJECT_DIR` is already set for it (the same variable the hooks use), and is safe against cwd drift by construction.

Separately, `hooks/stop-guard.sh:155-157` **already contains a mechanical backstop for exactly the consequence of this failure**, independent of its cause:

```bash
elif [ "${active_crew:-0}" -gt 0 ] && [ "$watcher_up" = 0 ]; then
    reason="You have crew in flight but no live watcher cycle. Arm one by running 'bin/watch-fleet' as a harness-tracked background task so its exit wakes you when crew need you, then you may stop."
```

This blocks the orchestrator's own `Stop` event whenever crew are in flight and no live watcher pid+beacon can be found, regardless of *why* the watcher is down (a failed arm, a crash, an OOM kill). This is real, working architecture, not a gap to build from scratch - the answer to "could stop-guard also assert a live cycle exists" is **yes, it already does.** What it does not close is the window between the arm silently failing and the orchestrator's own turn next attempting to end - during that window (bounded by how long the orchestrator keeps working before it tries to stop) the fleet genuinely is unsupervised. `stop-guard.sh` is also registered only in this repo's own project `.claude/settings.json`, so it is scoped to the orchestrator's own top-level session; a lead has no exact equivalent (a `Stop` hook is project-scoped, and a lead's own project root, e.g. `/home/greer/github/skills`, typically has no `.claude/` directory of its own - confirmed for this exact repo). Leads are not exposed to *this* specific failure (they already use `$WINGMAN_BIN`), so this residual gap is lower urgency, but it means a lead whose own arm fails for some *other* reason has no analogous backstop today.

## Recommended fixes, ranked

### Defect A

**Settled (human decision, 2026-07-30): the chosen fix is the thorough one, not the cheap one.** Of the three approaches this report originally ranked, the human deliberately chose the broader, behavior-changing option over the cheaper narrow one - explicitly to protect the whole send, not just the `C-c` step. The full scope below is the chosen fix's actual implementation surface, not an aspiration; the "considered, not chosen" items after it are recorded so an implementer does not re-litigate or re-derive them.

1. **(Chosen - medium, behavior change)** Generalize `wm_tmux_pane_ready` (`bin/lib/common.sh:544`) to return a third refusal code - alongside its existing 0 (ready) and 2 (dialog-shaped, refuse) - whenever a liveness probe (reusing `_probe_execution`/`_longest_running_descendant`, `bin/lib/wm-state.py:1257-1406`, already built and already exposed via `wm-state.py stall-check --pane-pid`) finds a live, CPU-active descendant process under the target pane's pid. This treats "busy running a tool" as a first-class refuse-and-retry state, exactly like the existing dialog-shaped refusal, and protects the entire send (the `C-c` clear **and** the subsequent type+Enter), not just the clear-keystroke.

   **Every caller of `wm_tmux_send_message` sits downstream of this change and needs its own retry/backoff decision for the new code - this is the full call-site scope, not a subset:**
   - `bin/crew-say` (`:76`) and `bin/crew-ask` (`:298`) - both are synchronous, invoked directly from a live agent turn wanting to notify or ask a peer. On busy, retry with a short, bounded backoff (the target's own tool call is presumably short-lived); if still busy once the bound is exhausted, fail distinctly from today's dialog-refusal message - today both `wm_die` with "resolve the dialog and retry" advice that is wrong for this case (there is nothing to resolve; it clears on its own). The busy-specific failure text should say so plainly ("the target is mid-tool-execution; retry shortly") rather than reusing the dialog wording.
   - `bin/crew-resume`'s resume-nudge (`:286`) - already passes `WM_CLEAR_KEYS=""`, but that only skips the clear-keystroke; it still calls `wm_tmux_pane_ready` first and so still receives the new refusal code. A just-resumed target is unlikely to already be busy, but the call site still needs to handle the code rather than assume it can never fire - same bounded-retry-then-fail shape as `crew-say`/`crew-ask`.
   - `bin/spawn-crew`'s opening-message delivery (`:509`) - also passes `WM_CLEAR_KEYS=""` but is equally downstream of `wm_tmux_pane_ready`. A freshly opened window is very unlikely to be busy (nothing has run yet), so the simplest correct handling is to feed a busy refusal into the delivery's *already-existing* queued-retry fallback (`spawn-crew`'s own "QUEUED for automatic retry by the watcher" path) rather than inventing new retry logic.
   - `bin/crew-standdown`'s `/remote-control` reconnect message (`:65`) - lowest stakes of the six; on busy, skip this cycle's reconnect attempt (log it) rather than blocking stand-down on a best-effort nudge.
   - `bin/watch-fleet`'s four send sites - the overdue-blocker message (`:924`, `:928`), the `/remote-control` reconnect retry (`:974`), and the stall-check nudge (`:1077`) - all already run inside `watch-fleet`'s own polling loop, so the cheapest correct policy is: on busy, skip sending this cycle and let the next poll iteration retry naturally. No new backoff logic is needed here; the loop's own cadence already provides it. This is also the site where the fix matters most - the stall-check nudge is what exists specifically to distinguish "still working" from "genuinely idle," so it must never itself manufacture a false stall by interrupting real, in-progress work.

   **Tradeoff (accepted as part of the decision):** every one of the six call sites above needs an explicit change, not just the primitive itself - this is real, distributed implementation work across `bin/crew-say`, `bin/crew-ask`, `bin/crew-resume`, `bin/spawn-crew`, `bin/crew-standdown`, and `bin/watch-fleet`, not a single localized patch.

2. **(Considered, not chosen)** Skip only the `C-c` step when a liveness probe finds an active descendant, leaving `wm_tmux_pane_ready` and its return contract unchanged. This was the cheaper option - no caller-side changes required at all - but the human chose recommendation 1 specifically because it leaves the type+Enter step unprotected against any subtler timing issue; not selected.
3. **(Superseded by recommendation 1 - do not implement separately)** Passing `WM_CLEAR_KEYS=""` for `bin/watch-fleet`'s stall-check nudge alone (`:1077`), mirroring `bin/spawn-crew:509`/`bin/crew-resume:286`'s existing override. Once recommendation 1 ships, `wm_tmux_pane_ready` itself refuses before the clear-keystroke is ever reached for a busy target - this narrower, single-site mitigation would be redundant work solving a case the chosen fix already covers for every caller, not just this one.

## Decisions (settled - do not re-open)

Both decisions posed by the original "Open Questions" section have been made by the requester and relayed directly. Recorded here so an implementer does not need to re-litigate them:
