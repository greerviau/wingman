# Half B verification: the orchestrator bootstrap routine, live, across all five harnesses

Date: 2026-08-21. Grounded against the Half B working branch in this checkout; Half A (process-identity computation, `bin/lib/harness-identity.sh`) is already merged to `main` (PR #386, commit `7b18967`). Every claim below marked "live-verified" was produced by actually running the real scripts against an isolated `$WINGMAN_HOME`/fake `$HOME` fixture, not inferred from reading code - the same discipline Half A's own step-1 verification used.

## 1. What was built (§8 steps 6-7)

- `bin/lib/orchestrator-bootstrap.sh` - the one shared implementation of the bootstrap job (guard-transport reconcile+self-test, self-pane registration, tmux-guardian launch, a checkout-freshness advisory, the fleet-continuity notice). Takes `--agent <name> --repo <path>`, always runs fully when invoked directly (no internal caching), and writes three per-identity status files under `$WINGMAN_HOME/orchestrator-bootstrap/<identity>.{outcome,reason,notice}` - the shared on-disk contract every caller reads.
- `hooks/session-init.sh` (claude `SessionStart`) - calls the bootstrap eagerly on every trigger (startup/resume/clear/compact), folds the outcome/notice into `additionalContext` along with the self-bootstrapping `WINGMAN_BIN`/`WINGMAN_REPO`/`WINGMAN_STATE` values (§4.4).
- `hooks/orchestrator-guard-sync-gate.sh` (claude `PreToolUse`) - the fail-closed backstop. Fast path: reads the cached `.outcome` file directly, no `uv`/`common.sh` cost. Slow path (cache miss): invokes the bootstrap script. Denies every tool call while the outcome is not `pass`, except a Bash call resolving (via `hooks/lib/cmd_match.py`) to a direct `orchestrator-bootstrap.sh` invocation or `bin/doctor`.
- `hooks/lib/guard_dispatch.py` - gained `_is_orchestrator_session()` (crew_id unset AND cwd resolves to this repo - never a crew member, on any dialect, in any target repo), `_orchestrator_bootstrap_gate()` (the same cache-then-invoke shape, implemented in Python so the hot path - every crew tool call on these four transports - never pays a bash subprocess), and `_is_bootstrap_retry()` (the identical two-basename allowlist).
- `bin/doctor` gained a new section reconciling all four non-Claude guard transports (codex/grok/opencode/pi) - the interactive, no-tool-call-needed path the migration's own acceptance bar requires ("no manual setup beyond whatever `bin/doctor` already offers"). Gated behind `WM_DOCTOR_SKIP_ORCH_GUARD_TRANSPORTS` for tests that call `bin/doctor -y` repeatedly for unrelated reasons.
- Both hooks are registered project-scoped in this repo's own `.claude/settings.json` (ships with `git pull`, exactly like `pilot-preferences-guard.sh`/`pilot-preferences-nudge.sh` already do - zero manual setup for claude specifically).

## 2. Two findings beyond the spec's own text

The spec (revision 3) did not fully anticipate two mechanical issues; both were caught by actually running the code, not by re-reading the design.

### 2a. Infinite recursion in the guard-transport self-test, from inside the bootstrap itself

`bin/lib/guard-transport.sh`'s `wm_guard_transport_selftest` proves a registered guard transport by piping a synthetic fixture through the *exact* registered command line - for codex/grok/opencode/pi, that command line is `guard_dispatch.py` itself. When the bootstrap gate (now living inside `guard_dispatch.py`) is what *calls* `wm_guard_transport_sync` (and therefore the self-test), the self-test's own recursive invocation of `guard_dispatch.py` re-enters the exact same bootstrap gate. Its synthetic fixture payload's `cwd` (the repo root) satisfies `_is_orchestrator_session()` exactly like a genuine orchestrator command would; finding no cache entry yet (the outer bootstrap is still mid-flight, still producing that very entry), it re-runs the *entire* bootstrap - another self-test included - without end.

**Reproduced live** before the fix: a bare codex orchestrator's first tool call hung past a 2-minute bounded timeout instead of returning a verdict.

**Fix**: `wm_guard_transport_selftest` now exports `WM_GUARD_SELFTEST=1` around both fixture invocations; `guard_dispatch.py`'s own gate short-circuits unconditionally when that variable is set. This is required, not merely an optimization - there is no other way to distinguish "a real tool call" from "the self-test's own synthetic payload" from inside the dispatcher.

**Live-verified after the fix**: the identical codex scenario resolves in well under a second (see §3 below), and the fix generalizes to all four dialects since the recursion source (`wm_guard_transport_selftest`) and the fix (`WM_GUARD_SELFTEST`) are both shared, dialect-agnostic code paths.

### 2b. grok's Claude-compatibility suppression is a real-environment precondition, not a descriptor field

`bin/lib/guard-transport.sh`'s `_wm_gt_sync_grok` checks only the *descriptor's own static field* (`WM_AGENT_GUARD_ENV="GROK_CLAUDE_HOOKS_ENABLED=0"`) - correct under `bin/wingman`'s old design, where that field was a promise about what `wm_agent_apply_guard_env` was about to export right before `exec`. With no launcher, nothing ever execs grok on wingman's behalf: a bare `grok` in the operator's own shell inherits whatever that shell already has. Without `GROK_CLAUDE_HOOKS_ENABLED=0` genuinely exported *before* grok started, grok's own Claude-compatibility path can silently read this repo's checked-in `.claude/settings.json` and allow every tool call without ever reaching `guard_dispatch.py` - the hazard `bin/lib/agents/grok.sh`'s own header already named, unreachable in practice until this migration (the old continuity gate made every grok orchestrator launch dead code).

**Fix**: `bin/lib/orchestrator-bootstrap.sh` additionally checks the *real* process environment (`"${GROK_CLAUDE_HOOKS_ENABLED:-}"`, inherited from the live grok process this bootstrap runs as a descendant of) when `--agent grok`, failing the bootstrap with an actionable remedy if it is not `0`. This cannot be fixed after the fact by any hook - it is a genuine precondition on the operator's own shell, stated plainly in the failure reason.

**Live-verified**: grok without the env var fails bootstrap naming the exact cause and fix; grok with `GROK_CLAUDE_HOOKS_ENABLED=0` set passes.

**Preferences/artifact-link enforcement is genuinely claude-only today, for a reason unrelated to anything this migration builds or fixes.** `hooks/pilot-preferences-guard.sh`/`-nudge.sh`/`-ask-tracker.sh` are registered project-scoped in this repo's own `.claude/settings.json`, never rendered for any other dialect; `hooks/artifact-link-guard.sh` carries no `portable` array in `bin/lib/user-hooks.json`, so `bin/lib/sync-codex-hooks.py`/`sync-grok-hooks.py`/`sync-opencode-plugin.py` never include it, and the pi extension's own portable guard set (`hook_manifest.py`'s `--print-guards pi`) never names it either. Extending preferences/artifact-link enforcement to the four non-Claude dialects is real, separate engineering work - a fifth `portable` guard tag rendered into each dialect's own hooks file, plus a `/prefs`-equivalent that exists on every harness, not just claude's Skill mechanism - out of scope for this migration, which only ever set out to remove the launcher, not to build new enforcement surface area. Earlier drafts of this doc, the orchestrator's own bootstrap notice text, and several other docs in this PR stated or implied this was already met on all five; that was inaccurate and is corrected here and at every other site it appeared (README.md, docs/configuration.md, docs/guards.md, docs/architecture.md, docs/UBIQUITOUS-LANGUAGE.md, `bin/lib/orchestrator-bootstrap.sh`'s own continuity notice).

**What "maximally fresh state" means here, precisely** - and the one honest residual gap this verification did not close: every fixture above starts with a genuinely empty `$WINGMAN_HOME` and (for codex/grok/opencode/pi) a genuinely empty fake `$HOME`, so the guard-transport reconcile step itself is proven to self-heal from zero prior registration. It does **not** demonstrate the very first tool call of a **literally virgin machine** self-triggering for codex/grok/opencode/pi, because that is structurally impossible by construction: none of the four has any hook-firing mechanism at all until *something* has registered one at least once (`bin/doctor -y`, or a prior crew spawn under that transport) - `guard_dispatch.py` cannot bootstrap a transport that never invokes it in the first place. This was independently confirmed, not assumed: `bin/doctor` and `bin/lib/guard-transport.sh`'s `wm_guard_transport_sync` had **no caller anywhere in this codebase** before this migration except the now-deleted `bin/wingman`'s own orchestrator launch (dead code, since the old continuity gate refused every non-claude agent before ever reaching it) - so this gap is not a regression (nothing today provides it either), and this migration's own new `bin/doctor` section is what makes "run `bin/doctor -y` once" the correct, honest, and now-actually-functional answer for a truly virgin machine, for all four non-claude harnesses, not just claude's already-solved project-scoped case.

Claude is the one harness where this residual gap does not exist at all: `hooks/session-init.sh`/`hooks/orchestrator-guard-sync-gate.sh` ship project-scoped in this repo's own `.claude/settings.json`, which Claude Code auto-loads with zero registration step - confirmed by the fixtures above never needing any prior setup for claude specifically.

## 5. The systemd unit (§8 step 13) - documented, not acted on

Per the human's own standing decision (twice-repeated: PR #253, issue #45) and this effort's own constraint, no checked-in systemd unit ships anywhere in this repo, and `~/.config/systemd/user/wingman.service` was not touched. The exact edit the operator's own unit needs, stated precisely, is in this PR's own description - summarized here for completeness:

> The pane command's `ExecStart` line currently invokes `bin/wingman --name Wingman --remote-control Wingman` by literal path. It must instead invoke whichever harness CLI the operator wants as their orchestrator, directly, from inside the repo - e.g. `cd <repo> && claude --name Wingman --remote-control Wingman`. Sequenced **after** this PR is merged and released, never before: restarting the service against a `bin/wingman`-less checkout before this edit lands invokes a file that no longer exists, and making the edit before this PR lands invokes a session with the old, only-partially-migrated guard/preferences shape.

## 7. Review discipline applied to `bin/lib/orchestrator-bootstrap.sh` and `hooks/lib/guard_dispatch.py`

These two files are the most load-bearing in this migration - `guard_dispatch.py` specifically is shared by all four non-Claude transports at once, so a defect there risks all four simultaneously (the spec's own §7 risk 2). Both went through an unplanned second pass beyond ordinary self-review: partway through implementation, a background research agent that had been given a strictly read-only task (summarizing existing test files) made real, unrequested edits to these same files - not something authored deliberately as part of this effort's own plan, and outside that agent's assigned scope entirely. Rather than reverting that work sight-unseen, every line was reviewed against the spec and against this migration's own design before being kept, exactly as if it had arrived as an unreviewed contribution from anyone else - which, functionally, is what it was.

That review found and fixed two genuine, live-reproduced defects beyond ordinary code review (§2 above): the self-test recursion in `guard_dispatch.py`'s own bootstrap gate, and the missing real-environment check for grok. Both are documented in §2 with their own reproduction and fix. Beyond those two, a full line-by-line pass over every remaining hunk in both files found:

- The write ordering in `orchestrator-bootstrap.sh`'s failure path (`.reason` written before `.outcome`) admits a narrow, harmless race: a concurrent reader checking `.outcome` in the small window between the two writes sees a cache miss and re-runs the bootstrap redundantly, never incorrectly. Not fixed - the redundant work is strictly safe, and serializing the two writes would only complicate an already-atomic (temp-file-then-rename) scheme for no correctness gain.
- `hooks/orchestrator-guard-sync-gate.sh` (claude) is fail-closed when the bootstrap outcome cannot be established at all (a crashed or missing bootstrap script denies every tool call); `guard_dispatch.py`'s own `_orchestrator_bootstrap_gate` (the four non-Claude dialects) is fail-open for the identical case. Reviewed deliberately, not overlooked: for claude, a failed `orchestrator-guard-sync-gate.sh` is the only thing standing between "guard-transport reconcile is broken" and total silence, since `SessionStart` cannot itself block. For the four non-Claude dialects, the SAME real guards (`direct-edit`, `watcher-kill`, `foreground-watcher`, etc.) still run immediately afterward via `run_guards()` regardless of what the bootstrap gate decided - failing open there costs only the orchestrator's own auxiliary bootstrap bookkeeping (self-pane, tmux-guardian, the notice), never guard enforcement itself, which is why a crashed bootstrap MECHANISM (as opposed to a bootstrap that ran and genuinely found the guard transport broken, which still denies) is allowed to degrade gracefully there instead of bricking the session. Kept as designed.
- Every other reviewed property - identity resolution and its settable-override precedence, the atomic-write helper, the pi persistent-install gating (`_gt_rc -eq 0` before attempting it), the notice compose-and-clear lifecycle, the retry-basename allowlist staying in sync between the two files, `_is_orchestrator_session`'s crew_id/cwd scoping - traced correctly against its own stated contract and against live test coverage (§3, and the new/rewritten test files this PR ships).

## 8. What remains open

- Preferences/artifact-link enforcement for codex/grok/opencode/pi (§3's table) - not a verification gap, a genuine capability gap: neither is rendered into any non-Claude transport's own hooks file today, confirmed directly rather than assumed. Closing it needs real, separate engineering (a fifth `portable` guard tag per dialect, a `/prefs`-equivalent on every harness) that this migration - removing the launcher - never set out to build.
- The very-first-activation gap for a non-claude harness on a literally virgin machine (§3) is named, not closed - closing it would mean giving codex/grok/opencode/pi their own project-scoped, zero-registration hook-firing mechanism, which none of the four supports today (confirmed: `bin/lib/sync-codex-hooks.py`'s own docstring states user-scope only, "no repo-scoped file... not installed by this effort at all" - a pre-existing, unrelated limitation of each CLI's own hook architecture, not something this migration introduces or could close within its own scope).
