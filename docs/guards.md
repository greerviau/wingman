# Guards, safety, and autonomous mode

How wingman's rules are enforced mechanically rather than by prompt discipline, and how crew run unattended safely.
Part of the [architecture reference](architecture.md); for day-to-day use see the [README](../README.md).

## Mechanical guards

The rules stated in prose across these docs and `CLAUDE.md` are also enforced mechanically, via Claude Code `PreToolUse`/`PostToolUse` hooks in `hooks/`, not left to prompt discipline alone:

- `hooks/no-direct-edit-guard.sh` blocks wingman's own top-level session (and any lead) from editing code or running long investigations directly - heavy work always goes to a crew member. It also recognizes the ordinary shell routes that run around the Edit/Write check to the same end: output redirection (`>`, `>>`, `&>`, `&>>`, `>|`, matched as a shell operator via `hooks/lib/cmd_match.py` so any command's output is caught, not an enumerated list), `sed -i`/`--in-place`, `tee`, and `cp`/`mv` onto a path inside a tracked git repo are all denied the same way a direct `Write` to that path would be (issue #171).
- `hooks/no-merge-guard.sh` denies `gh pr merge` and equivalents from every crew session unless that specific effort was granted `--allow-merge` - and, once granted, also requires verifiable evidence of a genuinely separate approving review (a real distinct-account `APPROVED` GitHub review, or the documented marker-and-roster-verified comment-fallback `VERDICT: approve` from a different, real `reviewer` crew member, cryptographically bound to that reviewer via a spawn-time hash commitment so a later comment cannot forge its way past the gate under a genuine reviewer's marker - issue #135) before the merge actually succeeds, unless the effort's `review_gate_waived` field was also explicitly granted (issue #132) - the waiver clears **this hook's own evidence check only**; it has zero effect on a forge-side branch ruleset requiring an approving review, which is a second, independent gate (see "Two merge gates, not one" below); `hooks/merge-attribution-tracker.sh` posts a PR comment attributing an authorized merge to the crew member that made it (a disclosure invariant, so it fires whenever a crew session actually merges - the opt-in auto-merge path, which requires `pr_comments=on` anyway - and is not itself gated on the preference), and `hooks/pr-open-marker-tracker.sh` prepends the same `<!-- wingman-crew:<id> -->` marker to the body of every PR a crew member opens via `gh pr create` **when `pr_comments=on`** (writing to a PR is opt-in; the marker's only consumer is this review/merge machinery). Inter-agent review is otherwise `crew-say`-native and writes nothing to the forge; because the merge gate reads its review evidence from the forge, an effort granted `allow_merge` needs `pr_comments=on` so a reviewer's verdict is recorded where the gate can see it.
- `hooks/no-watcher-kill-guard.sh` denies a `kill`/`pkill`/`tmux kill-window`/`tmux kill-session` whose target resolves to a live `watch-fleet` cycle, so the wake loop's own process can't be killed by accident. Herdr endpoint close operations remain backend-specific and must target the recorded pane.
- `hooks/no-foreground-watcher-guard.sh` denies a Bash call that arms `bin/watch-fleet`/`bin/pr-watch` (any form other than the read-only/one-shot `--status`/`--stop`/`--classify`/`--clear-standdown`/`pr-watch --once`/`-h`/`--help`) unless it carries `run_in_background: true`, and denies every detached form (`nohup`, `setsid`, a trailing bare `&`) outright even with `run_in_background: true` - both block until an event fires, so running one any other way wedges the session indefinitely with no mechanical signal visible to the stall detector (issue #202). It also denies an arming `watch-fleet` call outright (regardless of `run_in_background`) while a `spurious-repeated` failure-budget standdown holds for this session's owner - never `pr-watch`, which has no standdown concept - so the refusal is structural, not merely a nag the model can read and override (issue #198; see "The `spurious-repeated` standdown" below). It fails closed on every path, including an internal parse error or an unreadable `$WINGMAN_HOME`, rather than ever silently allowing an unverified command through - a genuinely absent marker is the one case that reads as a definite "no standdown" rather than a failure. `wm_state wedge-check`, called from `bin/watch-fleet`'s own poll loop, is the independent detection backstop for whatever this hook misses (not registered yet, or a shape it cannot parse) - see [architecture](architecture.md)'s wake-loop section for the full two-signal (pane continuity + matching descendant) design.
- `hooks/no-foreground-poll-loop-guard.sh` denies a Bash command containing an unbounded `while`/`until` loop with a `sleep` invocation anywhere in it, unless it carries `run_in_background: true` - a hand-rolled foreground polling wait has no independent timeout, so if its own exit condition is wrong (or the signal it waits for never arrives) it blocks the calling session's turn forever, unable to read incoming messages or self-diagnose (issue #268: two crew sessions did exactly this and cost roughly four hours combined - one on a `pgrep -f` self-match against its own command line, the other on a sentinel file a different process never wrote). It never blocks a `for` loop (naturally self-bounding) or a `while`/`until` loop with no `sleep` invocation anywhere in the command, and - like the foreground-watcher guard above - has no override flag, since reissuing the identical command with `run_in_background: true` is always available and always removes the risk. `wm_state loop-wedge-check`, called from the same `bin/watch-fleet` poll loop right alongside `wedge-check`, is this hook's own detection backstop: the identical pane-continuity-plus-matching-descendant signature, generalized to a second `--proc-re` pattern (a `while`/`until` keyword followed by a `sleep` invocation in a descendant's own `ps` command line, default `WM_LOOP_WEDGE_PROC_RE_DEFAULT`) so it recognizes the loop by what it says in `ps`, not by whether it happens to be consuming CPU - the same reasoning `wedge-check` already applies to a foregrounded watcher, since a spinning polling loop forks short-lived `sleep` children the entire time it is wedged and would otherwise read as "alive" to the generic stall probe forever.
- `hooks/no-interactive-prompt-guard.sh` denies `AskUserQuestion`, `EnterPlanMode`, and `ExitPlanMode` outright for every crew session (worker or lead) - only the top-level wingman session is ever actually watched by a human in real time, so a crew session calling one of these would hang waiting for a choice nobody is present to make, or have a later-arriving keystroke misread as input to an unrelated pending dialog. The denial redirects to `playbooks/_status-contract.md`'s `blocked` state instead (see "`blocked` for a human dependency" there).
- `hooks/no-worker-spawn-guard.sh` mechanically enforces both halves of the depth cap (`CLAUDE.md`: pilot → wingman → lead → worker, a lead spawns workers but not further leads): it denies `bin/spawn-crew` outright from any worker crew type (`developer`/`reviewer`/`architect`/`software-analyst`/`research`/...), and denies it from a lead too the moment the target is itself a `lead` - a worker with a genuine need for another crew member reports it to its own owner instead.
- `hooks/api-outage-spawn-guard.sh` denies new crew spawns while a fleet-wide API outage is detected as active.
- `hooks/usage-limit-spawn-guard.sh` denies new crew spawns while a fleet-wide usage-quota window is approaching its cap or the pilot chose to wait for it to reset; both this and the outage guard share their `PreToolUse` machinery (`hooks/lib/spawn_pause_guard.py`) rather than duplicating it.
- `hooks/artifact-link-guard.sh` and `hooks/artifact-publish-tracker.sh` enforce the Artifact-publish contract - a markdown deliverable is published as a hosted link only when the pilot asked for that and a content scan passes.
- `hooks/pilot-preferences-guard.sh` denies every other tool call in a fresh run until the onboarding-preference questions are answered (see "The preferences gate" below).
- `hooks/denial-report-guard.sh` (a `Stop` hook, crew sessions only) blocks the Stop the moment a crew session's own transcript shows a `toolDenialKind: "user-rejected"` tool-call denial it has not already reported - the mechanical backstop for `playbooks/_status-contract.md`'s "a tool call of yours was denied and no rule anywhere tells you what to do about it" case (issue #214). `user-rejected` is the one denial kind that carries no remedy of its own (unlike `permission-rule`, which carries the denying hook's own text, or `automode-blocked`); it covers both a live interrupt of an in-flight tool call and an ungranted permission in an unattended session, and the block names which one occurred. Deduped per (crew id, denial record uuid) via `$WINGMAN_HOME/denial-seen-<id>.json`, so a given denial only ever blocks one Stop. Fails **open** on any parse/IO problem - the opposite of this repo's fail-closed guards, since this gates ending a turn rather than an action that must not happen.

Not a hook, but the same "mechanical, not prose" discipline: `bin/spawn-crew`, `bin/crew-takeover`, and `bin/crew-resume` all bake a `claudeMdExcludes` entry (via the shared `wm_claude_md_excludes()` helper) into every `claude`-descriptor crew launch, so wingman's own root `CLAUDE.md` - the orchestrator's own first-person persona - never auto-loads into a crew session's context. This is the mechanical counterpart to the `TARGET_IS_WM_REPO`-gated prose disclaimer (issue #69) `bin/spawn-crew` also injects into a crew member's system prompt: the disclaimer tells a member to disregard the file if it sees it, while this exclusion stops it from being loaded at all (issue #213).

Also not a hook, and deliberately not one: `bin/crew-say`'s `--ack-constraints` gate (issue #192) refuses a message to a crew member carrying one or more recorded `constraints` unless that flag is also passed, reprinting every constraint on refusal.
It lives inline in the script itself rather than as a registered `PreToolUse` hook because `crew-say` is already the sole sanctioned path for injecting a follow-up message into a crew member's session (mirroring where the team guardrail itself is implemented, in that same file) - there is no second, unguarded route into a live session's pane this gate would need to also catch.
It deliberately does not attempt to judge whether a given message actually relaxes a given constraint (that would require judging arbitrary natural-language content, the one class of check this project consistently keeps out of its guards - see the catalog above); it only guarantees the constraint text cannot be absent from the sending session's own context when the call is made.
The identical reprint-and-require-a-flag shape gates the record's own clear path too: `wm_state crew-set --clear-constraints` on a non-empty record refuses without `--confirm-clear`, so the record this whole mechanism depends on can never be silently emptied by the same session that would otherwise want to relax it.
See `CLAUDE.md`, "A pilot constraint is not yours to relax."

Each of these exists because relying on the equivalent prose instruction alone had already failed at least once in this project's history; the hook is a backstop, not a replacement for the playbook text.

Every Bash-inspecting guard above matches the *resolved* command of each `;`/`&&`/`||`/pipe segment via the shared recognizer in `hooks/lib/cmd_match.py`, which sees through `env`/`sudo`/`uv run`/wrapper-shell `-c`/`eval` wrappers before matching - so `bash -c "gh pr merge 5"` and `eval "gh pr merge 5"` are caught the same as the unwrapped form (issue #168).
A shape that carries the real command as data for another program to execute instead of typing it directly (`xargs <cmd>`, `find ... -exec <cmd> ;`, a command piped into a shell) remains out of its reach; see the module's own docstring for the full list of documented gaps.

### The `spurious-repeated` standdown

The consecutive-failure budget (default 3, `WM_SPURIOUS_BUDGET_COUNT`) trips when `bin/watch-fleet` dies that many times in a row with no successful cycle in between. The trip itself - not any downstream consumer - writes a durable standdown marker (`$WM_HOME/watch.suppressed`, or the owner-scoped `watch-<key>.suppressed`), inside `--classify`'s own budget-trip branch: this way the standdown exists no matter which caller observed the trip, whether that is `hooks/stop-continuity.sh`'s own accounting, a lead's model-driven `/watch` classify, or a bare diagnostic `bin/watch-fleet --classify` call (issue #198).

Three things honour the marker once it is written, all reading the identical composed text (line 2+ of the marker file):

- **`hooks/stop-guard.sh`** nags with it on every subsequent Stop event while it holds, checked ahead of the kill switch (`WM_STOP_AUTOARM`) rather than after it - the kill switch means "do not auto-arm", never "ignore a deliberate standdown". **`hooks/stop-continuity.sh`** honours the same marker at its own step 7 (`:530`), but silently: it re-asserts the owner's `blocked` status and exits without arming, leaving the persistent surfacing to `stop-guard.sh`. Its own kill switch is checked first (`:74`), so `WM_STOP_AUTOARM=0` short-circuits it before the marker is ever read.
- **`hooks/no-foreground-watcher-guard.sh`** denies an arming `watch-fleet` Bash call outright while it holds (see above), so the refusal cannot be overridden by a model that reads the nag, correctly identifies it as deliberate, and arms anyway - #198's own incident.
- **The composed text itself** deliberately never instructs the model to arm; it splits a pilot-facing diagnosis-and-remedy from a model-facing "do not arm" instruction, so the standdown's own delivered text can no longer tell the model to dissolve it.

The marker is **run-scoped**: its first line is the arming run's `$WINGMAN_RUN_ID`, and it is honoured for the current run if that stamp matches, is empty, or the current session has no run id to check against at all - a marker stamped by a different, presumably-ended run reads as inactive. It is otherwise **un-time-bounded** - once tripped, it holds indefinitely, by design, so a wedged fleet does not silently regain an auto-arming watcher just because enough Stop events passed.

Two ways out, both pilot-directed: `bin/watch-fleet --clear-standdown` removes the marker without arming anything itself (fleet continuity re-arms on the next Stop event, which is the only path that produces a genuinely supervised cycle - a bare arm from a human's own terminal is not harness-tracked and wakes nobody); or a fresh run, since the marker is scoped to the run that tripped it.

### Which identities are claims and which are proofs

Two different strengths of identity coexist in these guards, deliberately:

- **Claimed:** `$WINGMAN_CREW_ID` is set by `bin/spawn-crew` into each member's own environment and then self-reported - the team guardrail's caller id (`crew-say`/`crew-ask`), a `crew-ask reply`'s `--responder`, and every `crew-set` are all trusted at face value. Any process could export another member's id; the threat model here is cooperative agents making mistakes, not adversaries, and the guardrails exist to catch confusion, not forgery.
- **Proven:** the merge review gate (issue #135) is the one place identity is load-bearing for an irreversible action, so it does not rest on a claim - a reviewer's comment-fallback approve must carry a `review-sign` proof bound to a spawn-time hash commitment only that reviewer's own process environment can produce.

Anything promoted in the future from "advisory" to "gating an irreversible action" should move from the claimed column to the proven one the same way.

The two spawn-pause guards (outage, usage-limit) react to the fleet-wide state machines described in [fleet resilience](fleet-resilience.md).

### Two merge gates, not one

Two independent gates stand between a crew member and a merged PR, and only one of them is wingman's own to grant (issue #190):

- **Wingman's own gate** - `hooks/no-merge-guard.sh`, above. Governed entirely by two per-effort roster fields: `allow_merge` and `review_gate_waived`. Both are wingman-side state; neither one is read by GitHub, and neither one has any effect whatsoever on the second gate below.
- **The forge's own gate** - a GitHub repository ruleset (or classic branch protection) on the default branch, which can independently require an approving review, required status checks, a linear history, and so on. This gate is enforced by GitHub, not by wingman; no wingman-side field reaches it at all.

**The single-account case is unmeetable by construction, not merely unmet.** Every crew session authenticates as the same forge account as the PR's own author (issue #50), and GitHub structurally refuses a self-approval - so a ruleset requiring `required_approving_review_count >= 1` can never be satisfied by any review a crew session itself could ever produce, no matter how it is granted. Waiving wingman's own review-evidence check (`review_gate_waived: true`) does nothing to change this: it only tells `hooks/no-merge-guard.sh` to stop requiring evidence of its own, it does not and cannot tell GitHub to stop requiring an approving review.

**The three operator-only remedies for the forge side** are: (a) the operator authorizes an admin override, merging through an existing ruleset bypass actor (`gh pr merge --admin`); (b) a second, genuinely distinct reviewer credential (a different GitHub account or App installation) approves the PR; or (c) the operator relaxes the ruleset itself. This project's own established practice is (a), granted per effort by the human - see `docs/UBIQUITOUS-LANGUAGE.md`'s "Admin override" for the exact shape.

**`--admin` is not a bypass of wingman's own guard.** `gh pr merge --admin` is still a `gh pr merge` invocation like any other, and remains fully subject to `hooks/no-merge-guard.sh` exactly as documented above - it still needs `allow_merge` (and, for the evidence check, either a real review or `review_gate_waived`). An available forge-side bypass is not a granted wingman-side one.

**`bin/lib/merge-block-diagnose.sh`** tells the two gates apart before an escalation is sent, the same role `bin/lib/git-freshness-check.sh` plays for checkout freshness (below): it classifies a blocked or failed merge attempt as wingman's own gate objecting, the forge's, both, or neither, names the remedy that actually applies to each, and states whether the authenticated account can use an admin override - all from cheaply-verifiable facts, never re-implementing the review-evidence check above (see the script's own header for why). `playbooks/_delivery.md`'s "Merge authorization" and `playbooks/common/lead.md`'s escalation discriminator both point a session at it before it escalates a blocked merge.

## The preferences gate

`hooks/pilot-preferences-guard.sh` (a `PreToolUse` hook registered project-level via this repo's checked-in `.claude/settings.json`, so it needs no `bin/doctor` step) denies every other tool call while any required preference is unanswered. A session that skips the onboarding ask is blocked rather than silently proceeding on defaults. The five keys, their prompts, and their accepted values are defined once in `hooks/lib/pilot-prefs.sh` (`WM_PREF_KEYS`); `/prefs` renders the ask.

**A preference answered in the [settings file](configuration.md#the-settings-file---configlocaltoml) is answered.** The guard reads preferences through `wm-state.py prefs-list`, which merges `config.local.toml`'s `[prefs]` table underneath the per-run answer store, so a fully-configured file means the gate is already satisfied on the first tool call and the guard never fires.

**A file-provided value is validated; a pilot-given one is not.** The settings file is hand-edited, so a value outside its key's vocabulary counts as *unanswered* and the question line names the offending value - a typo surfaces as a question instead of propagating as though the pilot had chosen it. A value cached during the run is taken as-is whatever it says: it came from an `AskUserQuestion` whose "Other" option can legitimately produce free text, and rejecting that would strand the guard in a deny loop no answer could clear.

**Every denial names its own way out.** The guard quotes a complete, absolute `pref-set` command with the run id already filled in, and verifies through its own allowlist that it will accept that command before printing it. Running what the denial prints clears the gate regardless of how the environment is set up - nothing depends on `$WINGMAN_STATE` being exported.

**It fails open rather than stranding the run.** If the guard cannot name a way out at all - the state engine is missing or broken, or its own escape command stops resolving - it stops gating, says so through a `systemMessage`, and records the reason in `$WINGMAN_HOME/prefs-guard-failopen-<session_id>`. Preferences then stay unanswered and every consumer applies its conservative default, so a broken install degrades loudly instead of deadlocking.

**An unattended launch needs no special handling.** With no directive there is nothing to act on; on the first directive the batched ask simply pends until a human attaches and answers, with fleet supervision still available through the guard's allowlist. This is measured behavior - see [`docs/analysis/2026-07-13-unattended-boot-launch-behavior.md`](analysis/2026-07-13-unattended-boot-launch-behavior.md).

## Hooks that need user-level settings

Most guards ship with this repo, but several must be registered in the user-level `~/.claude/settings.json` because they fire inside crew sessions whose project root is some other repo entirely - a project-level entry in this repo's own `.claude/settings.json` never loads there. `bin/lib/user-hooks.json` is the declarative manifest of every one of them; `bin/lib/sync-user-hooks.py` reconciles it against `~/.claude/settings.json`, and **runs automatically, fail-closed, at every point a Claude Code session is created** - `bin/wingman`, `bin/spawn-crew`, and `bin/crew-resume` all reconcile before the session starts, so a merged guard is an active guard with no human step in between (issue #241). `bin/doctor` remains the interactive path: it registers the identical set (still via `bin/lib/install-user-hook.py`) as part of onboarding, and a behavioural test keeps the two from drifting apart.

- `hooks/no-direct-edit-guard.sh` - the delegation guard, for wingman's own top-level session and any lead, regardless of which repo it launches in.
- `hooks/no-worker-spawn-guard.sh` - the worker-spawn depth-cap guard, for every crew session regardless of which repo it launches in.
- `hooks/artifact-publish-tracker.sh` + `hooks/artifact-link-guard.sh` - the Artifact-publish contract pair.
- `hooks/no-merge-guard.sh` + `hooks/merge-attribution-tracker.sh` - the merge-authorization pair.
- `hooks/pr-open-marker-tracker.sh` - marks every PR a crew member opens with the same attribution marker.
- `hooks/no-watcher-kill-guard.sh` - denies killing a live `watch-fleet` cycle from any session.
- `hooks/no-foreground-watcher-guard.sh` - denies a foreground or detached `watch-fleet`/`pr-watch` arm from any session, and denies an arming `watch-fleet` call outright while a `spurious-repeated` standdown holds.
- `hooks/no-foreground-poll-loop-guard.sh` - denies a foreground `while`/`until`+`sleep` polling loop from any session.
- `hooks/no-interactive-prompt-guard.sh` - denies `AskUserQuestion`/`EnterPlanMode`/`ExitPlanMode` from every crew session.
- `hooks/api-outage-spawn-guard.sh` - pauses new spawns during a fleet-wide outage.
- `hooks/usage-limit-spawn-guard.sh` - pauses new spawns while a fleet-wide usage-quota window is approaching its cap. (The other half of this detection pair, `bin/lib/usage-statusline.py` registered as the `statusLine` capture command, is not a hook and is not in the manifest - it stays registered by `bin/doctor` only, since unlike a hook it never changes across pulls.)
- `hooks/stop-guard-crew.sh` + `hooks/stop-continuity-crew.sh` - extend the `#185` fleet-continuity Stop pair to crew sessions in any repo.
- `hooks/denial-report-guard.sh` - the denied-tool-call backstop, for every crew session regardless of which repo it launches in.

**Six of these are also portable to the four non-Claude agent CLIs** (`codex`, `grok`, `opencode`, `pi`) - the delegation, watcher-protection, outage-detection, usage-limit, foreground-watcher, and foreground-poll-loop guards, marked in `bin/lib/user-hooks.json` with a `portable` array naming which dialects they render for, so the triage lives once, in the manifest, rather than hard-coded separately per reconciler. All the actual policy stays in `hooks/lib/guard_policy.py`'s `evaluate_*()` functions; `hooks/lib/guard_dispatch.py` is the one shared entry point every non-Claude dialect invokes, translating that dialect's own payload shape into the same normalized input the Claude-only `.sh` hooks build and translating the decision back into that dialect's own deny/allow contract. A dedicated reconciler installs each transport at user/global scope only (no project-scoped file for any of them): `bin/lib/sync-codex-hooks.py` (`$CODEX_HOME/hooks.json`), `bin/lib/sync-grok-hooks.py` (`$HOME/.grok/hooks/wingman.json`, personal scope - grok's own trust gate applies to project-scoped hooks, not this one), and `bin/lib/sync-opencode-plugin.py` (renders a JS plugin template to `$HOME/.config/opencode/plugins/wingman-guard.js`); `pi`'s transport installs nothing at all - the extension ships in the repo and loads via a launch flag. **Every transport is verified by executing it, not by inspecting it**: the shared self-test (`bin/lib/guard-transport.sh`) runs the exact command line that was registered against two synthetic payloads whose verdicts are known in advance (a bare arming `bin/watch-fleet` with no `run_in_background`, decided by the crew-id-independent foreground-watcher guard so it can never pass vacuously in the orchestrator's own preflight scope; a bare `ls`, which passes every guard in the set) and asserts both denied/allowed correctly - registration proves a hook is named somewhere the CLI will read, never that the CLI actually invokes it on a real tool call. `bin/wingman` runs this per-transport install-and-verify for its own resolved orchestrator agent (`$WM_ORCH_AGENT`) before its first tool call; none of it is wired into `bin/spawn-crew`/`bin/crew-resume` for crew sessions yet, and the project guard scope above (the fleet-continuity Stop pair, the onboarding-preferences trio) is not installed for any non-Claude transport either - both are stated preconditions on that follow-on, not silent gaps, since every non-Claude orchestrator launch is refused before either could ever fire (see the continuity gate below).

**A second, separate gate governs whether the orchestrator can run on a given CLI at all: fleet continuity.** Wingman's wake loop needs two Claude-Code-specific harness features - `asyncRewake` on a Stop-hook entry (what re-invokes the session after a long block) and `run_in_background` on a Bash tool call (what arms a watcher without wedging the turn) - and no non-Claude CLI has a wired equivalent for either yet, so `bin/wingman` refuses to start the orchestrator on any of them (`$WM_AGENT_CONTINUITY_TRANSPORT` empty), independent of whether that CLI's guard transport is built and verified. This gate runs *before* the guard install above, deterministically and with no side effects, specifically so a curious `WM_ORCH_AGENT=codex` run can never permanently register wingman's guards in an operator's own global config - several of the portable guards above have no crew-id gating at all - only to then refuse to launch anyway. The refusal names the gap at its true strength: **not built**, never "impossible" - `pi`'s own extension API has been shown, hands-on, to carry the primitives a wake loop needs (`agent_settled` as the re-arm signal, a blocking wait held by the extension itself rather than by a model-issued tool call, and `sendUserMessage` to re-invoke the session - see `docs/analysis/2026-08-17-pi-wake-loop-probe/`), so building a `pi` continuity transport is a reachable, evidenced follow-on, not a dead end; the other three CLIs' own primitives were not probed at all, and are labelled that plainly rather than assumed either way.

**If a guard fires late.** `bin/lib/sync-user-hooks.py --check --report --settings ~/.claude/settings.json` lists anything the manifest expects that is not yet registered - the diagnostic for "a guard hook that should be active isn't." A registration written mid-run never retrofits an already-running session; Claude Code binds hooks at session start, so a pilot whose checkout was stale when their session started needs a restart, not just a pull.

**A `stop-continuity`/`stop-continuity-crew` `timeout` change is the one registration-drift case with a silent failure mode instead of a loud one** (issue #231): the hook killed AT its own registered `timeout` has its exit code discarded, so a session that keeps its old, smaller `timeout` past a change - because it was already running when the change landed - goes dark on fleet continuity with nothing to notice by, until it restarts. **Restarting every such session is required, not merely advisable** - the exposure is bounded to at most one silently-discarded kill per session (issue #248), not indefinite. The harness's own timeout kill is a trappable `SIGTERM`, not `SIGKILL`: the hook's TERM/INT trap measures its own elapsed lifetime and stamps it to a run-scoped record before forwarding the kill, so the FIRST invocation killed under the stale, still-old binding witnesses its own real timeout directly and pins it for the rest of the run - every later invocation clamps to that direct measurement instead of the stale on-disk value, durably, not merely until the next clean exit. Only when no such measurement exists (and no dead in-flight marker left behind by a genuine, untrappable `SIGKILL` either) does the hook fall back to reading its own registered `timeout` at the top of every invocation (the minimum found across the project- and user-scope settings files, falling back to the historical 600s if neither can be read) - but that value is the CURRENT on-disk registration, which moves in the same change that ships the new script. A session already running when a `timeout` change lands keeps executing the new script off disk while its own harness binding still kills it at the OLD, smaller timeout - and by the time its next Stop event reads the clamp, the on-disk file already carries the NEW, larger one, so this fallback path alone computes a lifetime sized for a binding that session does not have and provides no protection for it at all; the measurement mechanism above is what closes that gap after the first kill. Both reconcilers (`bin/lib/sync-user-hooks.py` and `bin/lib/install-user-hook.py`) rewriting a stale `timeout` in place (rather than reading it as "already registered" forever) only sharpens the on-disk fallback's own exposure: its genuine protection is limited to the narrower, transient window before a reconcile has caught a given scope up - crew-scope, before the next spawn/resume - or an unreadable/missing settings file, not the general "forgot to restart" case.

## Checkout freshness (advisory, not a hook)

Not every risk this project has hit can be intercepted by a `PreToolUse` hook: "about to assert that file X currently does/doesn't do Y" is a claim made in prose, inside a plan or a review finding, not a distinguishable tool call the way `gh pr merge` or an unpublished-artifact report is. This is the first of two advisory diagnostics in this file built on that same shape - the second, `bin/lib/merge-block-diagnose.sh` above, tells the two merge gates apart before an escalation is sent, for exactly the same reason: which gate is objecting is a claim a session would otherwise have to piece together from several sources, ad hoc, rather than a single distinguishable tool call a hook could intercept.
A repo-scoped crew session other than `developer` (which already isolates into a fresh worktree every run) is `cd`'d directly into the target project's existing checkout, which can silently lag `origin/<default-branch>` if nobody has fetched or pulled it recently - a stale read has already produced one confirmed false finding, filed and then retracted as issue #142.
`bin/lib/git-freshness-check.sh` makes the fix to this - checking freshness before making such a claim - cheap and consistent instead of an ad hoc `git log`/`git status` improvisation: it fetches `origin` (read-only against the working tree, index, and `HEAD`) and reports whether the checkout as a whole is caught up with `origin/<default-branch>`, plus, given path arguments, whether each named file's content specifically differs between `HEAD` and `origin/<default-branch>`.
`playbooks/_status-contract.md`'s "Your checkout is a claim, not verified freshness" is the shared convention that tells every git-backed session to run it before asserting a file's current state, with targeted pointers at the three points in the software-development playbooks where this risk is most concentrated (`software-analyst.md`, `reviewer.md`, `architect.md`).

## Untracked `docs/` content at stand-down (advisory, not a hook)

A related exposure, also not interceptable by a `PreToolUse` hook: a `lead` works directly in the shared repo checkout rather than a worktree of its own (only `developer.md`'s "Isolate" step ever creates one), so a plan or review-findings file it writes to `docs/` can sit untracked in that checkout indefinitely - one `git clean -fd` from gone, with nothing surfacing the risk before this (issue #205).
`bin/lib/untracked-docs-check.sh <repo>` reports untracked files under `<repo>/docs/`: exits 1 with a warning naming the count and paths on stderr when it finds any, exits 0 printing nothing when `docs/` is clean or `<repo>` is not a git repo at all (the two are deliberately indistinguishable - this is a best-effort backstop, not a repo-validity check).
`bin/crew-standdown` calls it automatically for every stood-down `lead` that has no worktree of its own on record - warning-only, never gating the standdown - and `playbooks/common/lead.md`'s "Handoff at stand-down" section asks a lead to run the same check itself before its closing report, so the exposure is named in its own handoff rather than only surfacing after the fact.

## Autonomous mode and interactive gates

Because no human sits at a crew member's terminal, `bin/spawn-crew` launches each member in its descriptor's own bypass mode (`WM_PERMISSION_MODE`, default `bypassPermissions`) so a gated tool call auto-approves instead of hanging on a prompt forever. The flag itself is per-CLI, composed from the descriptor's `WM_AGENT_BYPASS_FLAG`: `--permission-mode <mode>` for `claude` and `grok`, `--dangerously-bypass-approvals-and-sandbox` for `codex`, `--approve` for `pi`, and an environment prefix rather than a flag for `opencode`.
Set `WM_PERMISSION_MODE=` (empty) to fall back to interactive prompting.

Two one-time interactive gates remain that no flag bypasses:

- Claude Code's Bypass-Permissions acceptance (once, ever).
- Each repo's first-time workspace-trust dialog (once per repo).

`bin/spawn-crew` checks both non-interactively before ever opening a crew window: `bin/lib/claude-gate-check.py` reads `skipDangerousModePermissionPrompt` from the user settings file and `projects[<repo>].hasTrustDialogAccepted` from `~/.claude.json`, the same two fields Claude Code itself persists on acceptance. The trust check walks from the repo path up through its ancestors, but stops at the nearest enclosing git repository's root - a plain directory inherits trust from any accepted ancestor up to `/`, while a git repo's own root never inherits trust from anything above it, only from its own entry or a path inside its own working tree (confirmed directly against the installed build: see `bin/lib/claude-gate-check.py`'s own trust-status doc comment for the probe method and CLI version).
`bin/doctor` is meant to have already cleared the (global) Bypass-Permissions gate during onboarding; `spawn-crew` re-checks it as a safety net, and always checks the (per-repo) trust gate fresh, since trust is granted per directory.
When both checks read as cleared, the spawn proceeds without a preflight refusal; when either reads as unmet, `bin/spawn-crew` refuses the spawn outright - no tmux window, no crew record - with a message naming the exact remedy.
The watcher's reactive pane-scrape detection (and a per-tool prompt when bypass is off) remains as a backstop for anything this preflight can't cover - a never-before-touched `--add-dir` target in a global-scope spawn, or a signal that drifts after a future Claude Code release - flipping the crew member to `blocked` and waking the pilot to approve once via `bin/crew-takeover`.
After that, crew in that repo run fully unattended.

These two gates are Claude Code's own built-in dialogs, distinct from `hooks/no-interactive-prompt-guard.sh` above: that hook stops a crew session's own turn from opening a *second*, independent human-wait state by calling `AskUserQuestion`/`EnterPlanMode`/`ExitPlanMode` itself, rather than covering a gate Claude Code presents outside any tool call.
