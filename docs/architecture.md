# Wingman architecture

In-depth reference for how wingman works internally.
For day-to-day use, see the [README](../README.md).

This document covers the core model - the wake loop, the deliverable lifecycle, and the crew hierarchy. Operational detail lives in focused companion docs:

- [configuration.md](configuration.md) - the launcher, the spawn recipe, model selection, and machine-local state in `~/.wingman/`.
- [guards.md](guards.md) - the mechanical `PreToolUse`/`PostToolUse` guards, checkout freshness, and autonomous mode.
- [fleet-resilience.md](fleet-resilience.md) - correlated fleet events, API-outage detection, and usage-limit-quota detection.
- [playbooks.md](playbooks.md) - crew types, categories, and local overrides.

## Overview

Wingman is a long-lived orchestrator session that delegates real work to a crew of independent agent sessions and is woken only when one needs attention. The pieces and how they relate:

```mermaid
flowchart TB
    pilot([Pilot]) <-->|"directives / reports"| wingman[Wingman<br/>orchestrator session]
    wingman -->|"bin/spawn-crew"| crew[Crew members<br/>independent agent sessions,<br/>each in its own tmux window]
    crew -->|"crew-set status"| state[("~/.wingman/<br/>crew.json · board.md · status files")]
    crew <-->|"crew-say / crew-ask<br/>(peer + owner messaging)"| crew
    watcher[["watch-fleet<br/>(the wake loop)"]] -->|"reads state + pane liveness"| state
    watcher -.->|"exits on blocked / review / done /<br/>died / stalled — that exit is the wake"| wingman
    wingman -->|"arms exactly one cycle"| watcher
```

State lives on disk, not in wingman's transcript, so it survives compaction and restarts; the watcher is event-driven, so an idle fleet costs no tokens. The rest of this reference details each piece.

## Remote Control

Claude Code's Remote Control lets a session be reached from `claude.ai/code` or the Claude desktop/mobile apps, not only via `tmux attach`.
Wingman wires this up in both directions:

- Every crew member launches with `--remote-control "wm-<id>"` (`bin/spawn-crew`, gated by `WM_REMOTE_CONTROL`, on by default) - the `wm-` prefix matches its tmux window name, so it reads identically in both places.
  This fails soft: on an account that can't use Remote Control, the session just starts normally with it quietly unavailable.
- A crew member's own dropped connection self-heals: `bin/watch-fleet`'s `remote_control_dropped_check` recognizes the disconnect banner in that member's pane and automatically retypes `/remote-control` to restore it.
- Wingman's own connection is watched differently, on purpose: `self_pane_check` can see wingman's own disconnect banner but deliberately never types into wingman's own pane - doing so from outside would race the very tool call meant to send the reconnect command.
  Instead it wakes wingman with an explicit `remote-control-dropped` event, and wingman tells the pilot to run `/remote-control` themselves.
- **A `died` member's Remote Control entry is stale.** An abrupt kill (a tmux or host crash, an OOM) gives the CLI process no chance to signal a disconnect, and no mechanism exists - no CLI subcommand, no API, no file-based signal - to deregister a Remote-Control-visible session from outside it once its process is gone (issue #96). A `needs-attention` note for a `died` member that had Remote Control enabled carries a caveat naming this, but the limitation is permanent: `bin/crew-list`'s status is always the source of truth for whether a member is alive, never Remote Control's displayed state.
- There is no reliable way to detect programmatically whether a given session is being watched locally or over Remote Control at any moment - see [`docs/analysis/2026-07-13-remote-control-transport-detectability.md`](analysis/2026-07-13-remote-control-transport-detectability.md) - which is why wingman asks once, up front, rather than guessing.

## Harness-agnostic by design

The **crew** coordination layer - tmux windows, the JSON status files, the watcher loop, and the board - does not depend on any one agent harness.
A crew member is just an agent CLI running in a tmux window that keeps its status file current.

The launch recipe is per-CLI **descriptor**-driven (`bin/lib/agent.sh`, `bin/lib/agents/<name>.sh`, issue #25): `bin/spawn-crew` resolves which descriptor to use (an explicit `--agent`, then `config.local.toml`'s `[harness.agent]` table, then `$WM_AGENT`, then the built-in default `claude`) and composes every launch flag from that descriptor's fields, rather than hardcoding one CLI's flag shape. Swapping harnesses means adding a descriptor and pointing selection at it - both isolated in `bin/lib/agents/`, never leaking into the crew coordination layer itself. `claude` and `pi` are the descriptors shipped so far (`opencode`, `codex`, and `grok` land alongside the rest of issue #25's per-CLI adapter work).
Wingman deliberately avoids a harness's native background-agent/attach/resume features to run or take over *crew*, because that would wed the crew layer to one harness. tmux attach is the takeover path precisely because it is neutral - it reaches whatever agent CLI is in the window.

The one thing that is legitimately harness-specific is **how the watcher wakes wingman** (see below) - a private loop between wingman and its own supervisor, not part of the crew layer.
Swapping harnesses means swapping that one arming primitive, exactly as it means swapping which agent descriptor `bin/spawn-crew` resolves; both are isolated, neither leaks into the crew coordination layer.

## The wake loop

A file on disk cannot rouse an idle session, so the only reliable way wingman is woken when crew need it is the **completion of a task the harness tracks**.

```mermaid
flowchart LR
    arm["Arm one cycle<br/>(harness-tracked bg task)"] --> block["watch-fleet blocks,<br/>absorbing benign<br/>'still working' updates"]
    block -->|"a crew member flips to<br/>blocked / review / done /<br/>died / stalled, or freezes"| fire["Exit with one reason line<br/>— that exit IS the wake"]
    fire --> handle["Wingman reads the reason,<br/>surfaces the event to the pilot"]
    handle -->|"re-arm after every fire"| arm
```

The watcher, `bin/watch-fleet`, is built for exactly this:

- It **blocks** - watching status files and window liveness, silently absorbing benign "still working" updates - and **exits with one reason line** the instant a crew member flips to `blocked`/`review`/`done`/`died`/`stalled` or freezes on a prompt.
  One run is one *cycle*.
- It is armed as a **harness-tracked background task** (e.g. Bash `run_in_background`), on its own, never bundled onto the tail of another command.
  Because the harness tracks it, its exit re-invokes wingman - that exit **is** the wake.
  It is never run detached (`nohup`/`&`); a detached process cannot wake an idle session.
  **It is also never run in the foreground** - `bin/watch-fleet`/`bin/pr-watch` block until an event fires, so any way of running one other than as a harness-tracked background task blocks the calling session on it indefinitely, with no mechanical signal that anything is wrong (issue #202). A foreground and a `run_in_background: true` Bash call are **indistinguishable from inside the invoked process itself** - identical stdio handle kinds, identical process ancestry (`bash` → `claude` either way), identical wrapper command line, identical environment - so this cannot be prevented, or even detected, from inside `bin/watch-fleet`/`bin/pr-watch`; prevention can only happen at the tool-call boundary, which is outside the process. `hooks/no-foreground-watcher-guard.sh`, a `PreToolUse` hook, is that boundary: it denies a Bash call arming either script unless `run_in_background` is truthy, and denies every detached form (`nohup`, `setsid`, a trailing bare `&`) outright even with `run_in_background: true`, since a detached process outlives the harness's own tracking and its exit wakes nobody. It fails closed on every path - an internal parse error included - never silently allowing an unverified command through. If a session cannot arm the watcher correctly, arming nothing is strictly better than arming it in the foreground: a missing watcher is recoverable, a wedged session is not.
- On each wake, wingman reads the reason line and `~/.wingman/wake`, surfaces the event to the pilot, then **arms exactly one fresh cycle**.
  The chain persists only if it re-arms after every fire.
- The arm's status line is truth: `armed` (a fresh cycle is now blocking), `healthy` (a live cycle already exists - do not start another), or a `blocked:/review:/done:/died:/stalled:` reason (it fired). `healthy` is run-scoped: each cycle stamps its arming session's `WINGMAN_RUN_ID` (`~/.wingman/watch.run`, owner-keyed), and an arm from a different run stops a live foreign cycle - e.g. an orphan from a prior, ended run, whose exit can never wake the current session - and arms its own tracked one, printing `armed` instead of adopting it. An arming session with no run id at all cannot certify ownership either way, so a live cycle then reads as `healthy` exactly as before.
  An atomic claim (an `mkdir`-based lock, verified with a write-then-read-back pass rather than trusting `mkdir` alone) makes two near-simultaneous arms resolve to exactly one live cycle, never two.
  The watcher checks for pending events the moment it arms, so a crew member that finishes in the gap between one fire and the next arm is surfaced by that arm, not lost.

A second arming path exists: `hooks/stop-continuity.sh`, an `asyncRewake`-registered Stop hook, drives this same loop tokenlessly, with no model turn spent specifically on arming (issue #185). It foregrounds `bin/watch-fleet` one self-bounded window (`WM_STOP_CONTINUITY_WINDOW`, default 480s) at a time, inside its own harness-tracked async process - but a quiet rollover or an unexpected watch-cycle death re-claims in place, inside a loop internal to that one invocation, rather than ending the turn for either (issue #231). The loop runs until its own lifetime budget would be exceeded, the fleet empties, or something genuinely worth reporting happens (a fire, a claim failure, a repeated-death standdown, an unwaited ask). The lifetime budget (`WM_STOP_CONTINUITY_LIFETIME`, default 3300s, measured from the hook's own start) is kept strictly inside the harness's own registered `timeout` (3600s) with real margin - a hook killed AT its own `timeout` has its exit code silently discarded, so overrunning it would end continuity until the model's own next natural turn. At the defaults this absorbs six windows per invocation, cutting an idle fleet's wake rate roughly 6x (about once every 48 minutes rather than every 8) without reaching zero: only a fresh Stop event can re-invoke an `asyncRewake`-registered hook, so budget exhaustion still exits 2 once per lifetime - the one wake that keeps the chain alive. The hook self-clamps that budget against the first of three evidence sources that yields a value, tried in that order (issue #248): a directly measured prior kill, a dead in-flight marker, or its own on-disk registration. The harness's own timeout kill is a trappable `SIGTERM`, not `SIGKILL` - the hook's TERM/INT trap measures its own elapsed lifetime and stamps it to a run-scoped record BEFORE forwarding the kill to its foregrounded child, so the first invocation killed under a stale registration witnesses its own real binding directly and pins it for the rest of the run; every later invocation clamps to that measurement instead of the stale on-disk value, durably, not merely until the next clean exit. Failing that, a dead pid left behind by a genuine, untrappable `SIGKILL` (no trap ran to measure anything) pins a conservative fallback for that one invocation's own clamp only, without altering stored state for later ones. Only once neither yields anything does the clamp fall back to reading the continuity entry out of both the project- and user-scope settings files and taking the minimum of whatever is found, or the historical 600s if neither can be read - but that value is the CURRENT on-disk registration, which moves in the same change that ships the new script, so this fallback path alone does not cover a session already running when a `timeout` change lands: that session's harness binding stays at the OLD value until it restarts, while the clamp it would read has already moved to the NEW one. Restarting every such session is still required, not optional - the measurement mechanism narrows the exposure to at most one silently-discarded kill per session, self-correcting from there, it does not eliminate the need to restart (see [guards](guards.md#hooks-that-need-user-level-settings) for the full accounting). Its concurrency guard is a self-owned, time-bounded in-flight marker, refreshed every iteration rather than fixed at entry so it stays fresh across a lifetime many multiples of one window, not `stop_hook_active` - the session-wide "did some hook block recently" fact is not a safe proxy for "is another instance of me already managing continuity for this owner," once rewakes are involved. A claim failure backs off for one window before retrying; a fleet that dies repeatedly (`spurious-repeated`) trips a standdown - written by `bin/watch-fleet --classify`'s own trip branch, not by this hook, so it exists no matter which caller observed the trip (this hook's own accounting, a lead's model-driven `/watch`, or a bare diagnostic call - issue #198) - that only a successful manual claim or an explicit `bin/watch-fleet --clear-standdown` clears. It is surfaced persistently by `hooks/stop-guard.sh`'s own no-watcher branch (with the standdown's own composed remedy text, not a generic nudge) regardless of `WM_STOP_AUTOARM`, for as long as it holds, and an arm attempt against it is denied structurally by `hooks/no-foreground-watcher-guard.sh`, not merely nagged against - continuity never silently disables itself. This is **not** an exception to the "never run detached" invariant above: the hook process itself is the harness-tracked entity under `asyncRewake`, never `&`-detached from it - only an untrappable `SIGKILL` landing on the hook itself (rare, given the self-bounded window) can still orphan the foregrounded child, a bounded, self-healing degradation rather than a new detached-arming pattern.

This was originally wired only for wingman's own top-level session, via this repo's own project-scoped `.claude/settings.json` - a lead's own team ran with no such backstop at all, fully model-driven per `playbooks/common/lead.md`. Crew sessions (including a lead's own session) now get the identical constraint too (issue #199), via a pair of thin wrapper scripts - `hooks/stop-guard-crew.sh` and `hooks/stop-continuity-crew.sh` - registered at **user scope** (`~/.claude/settings.json`) rather than project scope, since a crew session's project root is almost always some other repo, where wingman's own project-scoped registration never loads. Each wrapper gates on `WINGMAN_CREW_ID` (set only for a crew session, never for wingman's own top-level one) and `exec`s straight into the real, completely unmodified `hooks/stop-guard.sh`/`hooks/stop-continuity.sh` - the gate lives in the wrapper specifically because a gate inside the shared scripts themselves would have no way to tell which registration invoked it, and would silently disable both hooks for wingman's own top-level session (which has `WINGMAN_CREW_ID` unset) along with everything they protect. A lead still arms its own cycle per `playbooks/common/lead.md` as the primary, model-driven mechanism; this is a backstop for the case that's ever missed, not a replacement for it. Since issue #319, this same tokenless backstop also covers a member's own `bin/pr-watch` cycle: when the current session's own crew record is `working`/`review` with a PR-shaped `delivery` and no live `pr-watch` beacon, the hook folds a second child into the identical claim/window loop and re-arms `bin/pr-watch` alongside (or instead of) `bin/watch-fleet` - see "The crew-level wake loop (PR shepherding)" below for `pr-watch` itself.

The watcher also detects a crew frozen on a permission or trust prompt - a terminal-UI stall the status files can't see - and flips it to `blocked`. A second, distinctly-worded regex (`WM_RESUME_PROMPT_RE`) layered onto the same generic dialog-shape detector recognizes one further freeze: the CLI's own "resume from summary?" menu, which a `claude --resume` relaunch of a long-transcript session can land on (issue #30). That gets its own specific `blocked` wording (needs one keypress via `bin/crew-takeover`) rather than the generic permission/trust one, so an automated resume attempt that silently froze there is never misreported as a healthy `working` member.
It detects a member gone silently idle (no pane output, no status update, no execution in its process tree) and, before flipping it to `stalled`, sends it a check-in nudge - a plain message into its pane, worded for an API/connectivity-error signature (a rate limit, a 5xx, a connection reset) if the pane tail shows one, generic otherwise. The nudge is retried, bounded by `WM_STALL_NUDGE_TRIES`, until its submit is confirmed (issue #236): a per-id marker records `confirmed` only once the composer visibly clears, or `pending` plus an attempt count while a submit could not yet be confirmed, and expires by TTL so a concluded episode's marker can never gate a later one. A confirmed nudge then waits a full cooldown window for activity before the flip; an unconfirmable nudge instead exhausts its retry budget, gets a best-effort (never verified) composer clear, and escalates on its own, with the `stalled` reason text stating plainly that the submit was never confirmed rather than claiming a nudge landed. This lets a transient outage, or any other self-resolvable hiccup, self-heal where possible instead of paging the pilot immediately.
The nudge itself is gated on the identical process-tree evidence the flip's own execution probe uses (`wm_state liveness-probe`, issue #234): a member whose pane holds a descendant that started well after the pane root - an armed `watch-fleet`/Stop-hook watcher, an in-flight tool shell - is demonstrably alive, so it is skipped by both the nudge and the flip, not merely the flip. A lead correctly parked waiting on its own reports is exactly this shape for as long as its delegates work; before this, only the flip excluded it, so the nudge alone still typed an unsolicited check-in message into an otherwise-correctly-idle pane. When a stall *does* flip on a member with one or more live direct reports, the reason text names that count and points at `bin/crew-say <id> <nudge>` rather than only `bin/crew-takeover`/`bin/crew-standdown`: the far more likely failure for that population is the member's own wake chain having died over a still-live sub-crew, not its agent.
The nudge also stamps a `nudged_at` timestamp onto the member's own status record (via the same per-poll `stall-check` call, not a second subprocess) **only on a confirmed send**, so a still-`working` member mid-self-heal renders as `working (self-heal nudge sent Xs ago)` in `crew-list`/`board.md` instead of a bare `working` - the nudge marker file was a private sidecar the watcher alone read, so this state used to be invisible to a human or an owning lead until it either resolved or escalated (issue #155). `wm_state wedge-check` (below) also tracks the elapsed time of the single longest-lived qualifying descendant process on every poll, for `working` and `blocked` members alike, independent of every other gate (a single outstanding tool call or background shell keeps Claude Code's own pane repainting via its "N shell(s) still running" indicator, so the idle gates may never trip at all) - relocated there from `stall-check` by issue #202, since it now needs to run for `blocked` members too: once that elapsed time crosses `WM_LONG_SHELL_WARN` (a generous, configurable render-time ceiling, default 20 minutes), the same rendering annotates `working (1 shell running Xm, longer than usual)` (or `blocked (...)`). Neither this annotation nor the nudge one ever causes a `blocked`/`stalled` flip on their own - both are purely informational, since a legitimately long build or test run is not itself an error.
A crew session also cannot itself open a second, independent human-wait state by calling `AskUserQuestion`/`EnterPlanMode`/`ExitPlanMode` - see [guards.md](guards.md)'s `hooks/no-interactive-prompt-guard.sh` - so the nudge-and-wait mechanism above exists for genuine idle self-heal, not as a workaround for a crew session stuck on a prompt nobody can answer.

`stall-check`'s polarity is silence: it flips a `working` member to `stalled` on no pane output, no status update, no execution. A session wedged foreground on its own `watch-fleet`/`pr-watch` arm (the guard above is the prevention; this is the backstop if that arm was never made, or predates the guard's registration) produces the *opposite* signature - a pane that never falls silent, mid-turn on a call that never returns - so `stall-check` cannot see it, and a `blocked` member is additionally skipped from `stall-check` entirely. `wm_state wedge-check`, called once per member per `watch-fleet` poll for both `working` and `blocked` members, closes this: it flips a member to `stalled` once its pane has repainted *continuously*, never idle at a prompt, for `WM_WEDGE_SECS` (default 1800s) of genuinely *observed* coverage, **and** its own status record has gone unwritten the same window, **and** a `watch-fleet`/`pr-watch` descendant of its pane has itself been running that long (matched via `WM_WEDGE_PROC_RE`, default `watch-fleet|pr-watch`). All three are required together: **descendant duration alone does not discriminate a wedge from a healthy backgrounded watcher** - a lead that armed its own cycle correctly has a descendant that blocks unboundedly for as long as its crew stays quiet, so it matches the duration signal identically to a wedge; only pane-repaint continuity is specific to being stuck mid-turn, which is why the check requires both signals rather than either alone. A pane observation gap longer than `WM_WEDGE_PANE_GAP` (default 60s, since a healthy pane's own longest continuously-live run saturates just past this by construction) resets the anchor, so a watcher outage never masquerades as continuity. On flip, any existing `blocker` is carried into the stall reason before the field is cleared, so a false positive never destroys an open question; the reason names the matched process, pid, and both durations, and points at `bin/crew-takeover`/`bin/crew-standdown`. The measurement backing the two thresholds - the longest continuously-live run a healthy pane produces versus a wedged one - is preserved in [`docs/analysis/2026-08-03-issue-202-wedge-measurement.md`](analysis/2026-08-03-issue-202-wedge-measurement.md).

When the **same** signal hits many crew at once - a mass death, a correlated API-error stall, an outage, or an approaching usage-quota window - the watcher collapses or escalates it rather than paging per member, and pauses new spawns where appropriate. That machinery is documented in [fleet-resilience.md](fleet-resilience.md).

## The deliverable lifecycle and `review`

A crew member is not spun down the moment its deliverable appears; one session sees a piece of work through from creation to final disposition.
The **state model is defined once** in the shared status contract (`playbooks/_status-contract.md`), which is appended to every crew brief; playbooks describe only the work, not how to move between states.

```mermaid
stateDiagram-v2
    direction LR
    [*] --> working: spawned
    working --> blocked: needs a human decision
    blocked --> working: answer relayed back
    working --> review: deliverable ready (announced once)
    review --> working: feedback / CI / a watched event
    working --> done: terminal condition met
    review --> done: terminal condition met
    done --> [*]: reaped (crew-standdown)
    note right of review
        live + surfaced: the member keeps
        running, watching an external condition
    end note
```

The status state machine (`bin/lib/wm-state.py`) encodes the same states:

- `LIVE_STATES = (working, blocked, review, stalled)` - a member in any of these is still in flight and stays on the board's Active list.
- `working` is active work in flight - producing, revising, or seeing through work (e.g. CI) that must conclude before the deliverable is ready.
  It is never surfaced, so summary refreshes here don't wake the pilot.
- `review` is the parked-and-waiting state: the deliverable is produced and surfaced, and the member is now watching an external condition it does not control (a PR merge, a plan approval).
  It is both **live** and **surfaced** - `needs-attention` (`ATTENTION_STATES`) announces it to the pilot once per entry, exactly as `blocked` is announced, but the member keeps running.
  A member moves back to `working` to act on an event (review feedback via `crew-say`, a CI failure) and returns to `review` when it settles.
  The dedup key `needs-attention` actually reads is `announced`, not `updated`: `announced` advances on a genuine transition into an attention state, and - for `review` specifically - also on a material change to its `artifact`/`blocker`/`delivery` pointer, but not on a same-status `review` refresh that only touches `summary`.
  `blocked` and `done` are unscoped by this gate: `--silent` is forbidden for them, so every non-silent call announces.
  This is why a re-delivery that answers feedback on an already-`review` deliverable must transition out of `review` and back (through `working`), not restate `--status review` directly: only the transition, or a changed pointer, re-announces.
  Idle time in `review`, or a same-status summary-only refresh, writes nothing new to surface, so a parked member never spams.
- `done` means the terminal condition is met and the member is ready to be reaped: a plan approved/handed off, or a PR merged/closed.
  A ready deliverable is `review`, never `done`.

The lifecycle is uniform across types - deliver → `review` → drop to `working` to act on feedback and back → `done` - and each playbook names its own deliverable, dependency-to-watch, and terminal condition; the contract supplies the state mechanics.

Wingman holds **no** waiting logic itself: it recognizes crew status updates and surfaces the meaningful ones, and it spins a member down in exactly two cases - the member reports `done` (the watcher detects it; wingman relays the outcome and reaps it with `crew-standdown` **in the same turn**, so `done` is transient on the roster and finished members never pile up), or the pilot stands it down explicitly.
Nothing else reaps a member.
*How long* and *why* a member stays alive after delivering is entirely the playbook's concern; wingman only avoids cutting it short.

## The crew-level wake loop (PR shepherding)

A developer member's "seeing it through" often means watching its own PR, and it uses the same wake primitive wingman uses on itself, one level down.
`bin/pr-watch` is **one available, forge-specific** dependency-watcher for PR-shaped delivery, not a mandated step: after opening a PR a member *may* arm it as a **harness-tracked background task** (never detached) to be woken on forge state.
It blocks, polling the PR through the forge CLI, and exits with one reason line (`merged` / `closed` / `changes-requested` / `ci-failed` / `comment` / `checks-passed` / `merge-ready`) the instant an actionable event occurs; that exit re-invokes the crew member, which acts and arms exactly one fresh cycle - the identical arm-one-cycle discipline as `watch-fleet`.
A defensive re-arm on the same PR is a no-op: the same pidfile+beacon shape `watch-fleet` and `crew-ask await` already use guards `pr-watch` too (issue #180), keyed by `$WINGMAN_CREW_ID` (a member watches at most one PR at a time) - a second arm finds the live cycle's pid alive and its beacon fresh, prints `healthy`, and exits rather than starting a rival loop.
Inter-agent **review** feedback, though, travels over wingman's own channel (`crew-say`) by default, not the PR: a reviewer reports its verdict to whoever commissioned it, and a parked developer is woken by that incoming message rather than by pr-watch spotting a comment.
The `changes-requested`/`comment` reasons therefore only carry review feedback when the human has opted into writing to the forge (`pr_comments=on`); in the default flow pr-watch is effectively just a CI/merge/close watcher, and a developer whose delivery has no forge signal to watch arms no watcher at all.
`checks-passed` fires once when the PR settles with nothing failing and nothing pending (all-green, or a repo with no CI) for the same head commit confirmed across two consecutive polls (issue #257), and - for a repo known to have CI configured at all - never off a rollup that is merely empty rather than genuinely resolved (issue #274) - and, when the forge confirms a non-zero checkSuite count for the exact head commit, never off an empty rollup at all, even without a local CI signal (issue #259) - which is what lets a member stay `working` through CI and be woken to move into `review` only when it is genuinely on the humans; it re-arms once checks go pending/failing and settle again.
`merge-ready` occupies that same slot and fires instead of `checks-passed` when the member's own crew record carries `allow_merge: true` - pr-watch re-reads that record fresh on every poll, so a mid-flight grant (the ordinary way autonomy actually gets granted, typically after a human already sees the PR sitting green) is picked up on the very next cycle with no dependency on any further PR-side event, closing the gap where a merge-authorized member could otherwise sit parked in `review` indefinitely with nothing left to wake it. On `merge-ready` the member attempts the merge as its next action rather than waiting to be prompted (`playbooks/_delivery.md`, "Merge authorization").

`merge-ready` is the point-wise fix for one sub-case of a broader gap: a `review` member is announced exactly once, and that is correct only for one being actively shepherded by something pollable. A member with nothing polling on its behalf at all - an analyst idling for pilot feedback, or a developer whose delivery has no forge signal to watch, or one that simply isn't currently running `pr-watch` - goes silent forever once that one announcement is acked, however long it then sits. `bin/watch-fleet` closes this generically (issue #187) with a bounded resurface: `bin/pr-watch`'s blocking loop touches a liveness beacon (`$WINGMAN_HOME/pr-watch-<id>.beat`) on every iteration, and each `watch-fleet` cycle calls `wm_state review-resurface-check`, which fires at most one reminder per `WM_REVIEW_RESURFACE_SECS` window (default 6h) for a `review` member whose beacon is absent or older than `WM_REVIEW_WAKER_GRACE`. The reminder's own cadence stamp lives in its own store (`review-resurfaced.json`), never touching the `#57` once-only dedup a live-watcher member still relies on, and its note is prefixed `REMINDER (` so wingman relays it as standing-work, not a fresh delivery event. A member with a fresh beacon - one currently under active `pr-watch` polling - is never eligible, regardless of how long it sits in `review`, so today's once-only behavior is otherwise unchanged. This 6h reminder is the long-horizon half of a now-two-tier safety net (issue #319): a short-horizon tokenless re-arm, bounded by one continuity window (`WM_STOP_CONTINUITY_WINDOW`, ~480s default), lives in `hooks/stop-continuity.sh` itself (see "The wake loop" above) and covers a `pr-watch` cycle that dies while a member is actively `working` or parked in `review` with a live PR-shaped `delivery`. Before this, that Stop-hook coverage existed only for `watch-fleet` (issue #199); after it, both watchers have it, and the 6h reminder remains the backstop for the population with nothing polling on its behalf at all (no `delivery` to watch, or one that was never armed in the first place). A deliberate side effect of folding both watchers into the same loop: a plain worker with no sub-crew but a live PR now also gets `watch-fleet`'s own fleet-wide outage/usage-limit signal coverage for as long as this loop stays alive on its PR's behalf - coverage it never had before, since it previously took the fast-path exit before `watch-fleet` was ever spawned at all.

`blocked` has the mirror-image problem (issue #194): a delegate that acts on its owner's answer but never transitions back to `working` leaves a resolved question sitting in `blocker`, and `needs-attention` (`hooks/stop-guard.sh`, `hooks/stop-continuity.sh`, `watch-fleet`'s own wake decision - all three read only through `cmd_needs_attention`) re-surfaces it as if it were still open. The fix is a second bounded muffle, structurally parallel to the `#187` resurface above but pointed the opposite direction - temporarily *withholding* a still-technically-`blocked` row rather than *reminding* about a `review` one gone quiet. Two inputs, both carried on the member's own status file and computed fresh on every `cmd_needs_attention` call (no store of its own, unlike `review-resurfaced.json`, since the comparison only ever needs the record's own three timestamps plus wall-clock `now()`): `blocker_set_at`, stamped by `cmd_crew_set` whenever the (possibly parked-composed) `blocker` text changes while the record is `blocked`, and cleared the moment it leaves `blocked`; and `last_delivered`, a `{sender_id: timestamp}` map written only by the `record-delivery` subcommand, which `bin/crew-say` and `wm_outbox_try_redeliver` both call on every *confirmed* delivery into a member's pane (never by the member's own `crew-set`). A `blocked` row is withheld while `blocker_set_at <= last_delivered[owner]` (the owner's reply landed after the blocker was set) **and** `updated > last_delivered[owner]` (the record has since demonstrably run a turn on that reply - a confirmed tmux submit only proves the message reached the pane, not that the recipient acted on it) **and** the elapsed time since the reply is under `WM_BLOCKER_ANSWER_GRACE` (default 900s/15min). Past that window the row resurfaces automatically with a `STALE? (` prefix, exactly the same "bounded, not permanent" posture as the `review` resurface's `REMINDER (` marker: a decision that is genuinely still open is never silenced for more than one window, full stop. `bin/crew-list` and the `/blocked` skill are a separate query path (`cmd_crew_list`, reading the roster directly) and are deliberately unaffected - a human explicitly asking "what's blocked" always sees ground truth, muffled or not.

A different, structural gap remains even with a fully healthy, armed watcher cycle: nothing compares a lead's own roster shape across cycles, so a lead whose team is stuck exactly the same way - N workers permanently parked in `review` with no reviewer ever spawned, or a delegate's own summary unchanged wake after wake - produces zero attention events forever, indistinguishable from genuine, healthy progress (issue #199). `wm_state forward-motion-check`, called once per `watch-fleet` cycle by an owner examining its OWN direct reports (wingman's own top-level cycle for a lead, or recursively a lead's cycle for one of its own sub-managers), closes this: for every `working` candidate with at least one active report, it hashes a signature of the candidate's own `(summary, blocker, artifact, delivery)` plus the sorted `(child_id, child_status, child_announced)` tuple of every active report, and persists an anchor (`forward-motion.json`) that resets the moment that signature changes. If the signature has been stable for `WM_FORWARD_MOTION_SECS` (default 30 min), the candidate's `working` children are given one last chance to prove otherwise (issue #244): `watch-fleet` hands the check a session-wide pane-pid snapshot (one `tmux list-panes -s` call), and for each such child it probes the process tree at that pid for genuine CPU spend over a sampling gap - deliberately the same CPU-delta evidence `stall-check`'s own branch (b) uses, never the cheap branch-(a) liveness probe, since a child merely parked on its own idle armed watcher always has a late-started descendant and would read "alive" under branch (a) alone, defeating the detector for its most ordinary population. A live child resets the anchor exactly like a genuine signature change; only once no working child shows measurable CPU spend does the candidate flip directly to `stalled` - reusing the exact status, with the same downstream routing (the board's Active list, `needs-attention`, `hooks/stop-continuity.sh`'s incident-runbook routing) every other `stalled` flip already gets, so nothing new needs to know about this path. Unlike the liveness `stall-check`, this is otherwise condition-agnostic: it requires no schema linking a developer's record to a reviewer's, and catches any "any wait" shape - a dropped fire, a reviewer nobody assigned, a CI run nobody is watching - by watching the shape of the roster rather than any one specific dependency.

`stalled` is the one status the supervisor imposes unilaterally, and until issue #235 it was also the only one nothing ever revisited: once flipped, no diagnostic looked at the record again, so a member that resumed activity - or whose wedge/forward-motion condition resolved - stayed flagged until a human noticed. `wm_state stall-recheck`, called once per `stalled` member per `watch-fleet` poll (immediately before the pane-diagnostic skip every other check in this section sits behind), closes this by re-running the SAME detector's own evidence recorded on the record's `stall` object at flip time (`{source, since, prev_status, prev_summary, prev_blocker, ...}`, written by every flip site through one shared `_impose_stall` helper) rather than a uniform liveness probe: a wedge-stalled or forward-motion-stalled member has a live process tree *by construction*, so a naive "is it alive" revert would silently delete both of those mechanisms outright. Each source's clearing predicate reads ONLY its own evidence and is written fail-closed throughout - unreadable, absent, or malformed evidence is always "not contradicted," never grounds for a revert - because a spurious clear rewrites `updated`, which closes the overridden detector's own re-flip gate for a full `WM_WEDGE_SECS`/`WM_FORWARD_MOTION_SECS` window. A single contradicting poll is never enough: `stall.clear_polls` must reach `WM_STALL_RECHECK_CONFIRMS` (default 2, hard-floored to 2 regardless of the setting - a watcher's very first poll for any member always reads as "pane changed," so a floor of 1 would clear every liveness stall on every restart) of *consecutive* contradicting polls before the record reverts; one agreeing poll in between resets the streak to zero. A revert is silent on the wake channel by design - it corrects the supervisor's own prior conclusion, so it fires nothing and never rewrites `$WINGMAN_HOME/wake` - except when it restores a `blocked` status, since the restored `blocker` is a genuinely open question nobody answered and re-announces exactly once through the ordinary `needs-attention` path. The only durable trace of a silent clear is one line appended to `$WINGMAN_HOME/stall-recheck.log` (`<iso> <id> <source> cleared after <N> polls`). Rendering always shows a `stalled` classification's own age (`stalled (flagged 3h12m ago)`, anchored on `stall.since` and falling back to the record's `updated` for a pre-migration record with no `stall` object at all), and additionally flags a recovery streak in progress (`; showing activity for 10s - classification may be stale`) so a pilot can tell a fresh flip apart from one that is about to clear itself, even against a fleet whose watcher has since died.

A cursor at `$WINGMAN_HOME/pr/<crew-id>.json` records what has already been surfaced, so a persistently-red build or an already-handled comment does not re-fire, and this session's own replies never wake it - identified by an anchored `<!-- wingman-crew:<id> -->` marker matching its own crew id, not by forge login alone (every crew session shares one forge login, so login alone would also drop a human's own genuine comments or a different crew member's own genuine review).
Firing advances only the fired dimension, so a co-occurring lower-priority event still surfaces on the next cycle.
The event-decision logic lives in `bin/lib/pr-eval.py` (pure, unit-testable with canned JSON); `bin/pr-watch` is the thin poll loop around it.

This keeps the two watch loops cleanly separated at different levels: `watch-fleet` is wingman's channel to its crew (forge-agnostic), `pr-watch` is a crew member's channel to the forge.
The forge-specific part is isolated in `pr-watch`'s `gh` calls, overridable via `WM_GH` (point it at another binary or wrapper), exactly as the agent launch recipe is isolated in `spawn-crew` behind its per-CLI descriptor resolution; a non-GitHub forge swaps this one script.
Analyst (and other non-PR) members have no external signal to poll, so they arm no watcher - they idle in `review` until the pilot's feedback arrives via `crew-say`.

## The crew hierarchy (leads)

Wingman's crew is a **tree**, with the pilot at the top. A large effort is owned by a **lead** - a crew member whose playbook is "be a manager for one effort." A lead runs the *same* intake → scope → spawn → supervise → report → escalate loop wingman runs, one layer down, over its own crew (a software-analyst, an architect, one or more developers, a reviewer). This is recursion over the existing primitives, not a parallel subsystem: the lead uses the same `bin/` scripts and the same watcher.

```mermaid

    pilot([Pilot])
    wingman["Wingman<br/>(owner &quot;&quot; — top level)"]
    analyst["software-analyst<br/>(direct spawn)"]
    lead["Lead<br/>(owns one effort)"]
    dev1[developer]
    dev2[developer]
    rev[reviewer]

    pilot --> wingman
    wingman -->|"parent = &quot;&quot;"| analyst
    wingman -->|"parent = &quot;&quot;"| lead

    subgraph cap[" "]
        lead
        dev1
        dev2
        rev
        lead -->|"parent = lead-id"| dev1
        lead -->|"parent = lead-id"| dev2
        lead -->|"parent = lead-id"| rev
        dev1 <-.->|"crew-say (peers)"| rev
        caplabel["depth cap: 2 crew layers"]
        dev2 ~~~ caplabel
    end

    classDef caption fill:none,stroke:none,color:#8a6d00,font-weight:bold
    class caplabel caption
```

Each layer sees only its direct reports (`blocked` escalates one hop up; a lead rolls a single line up to wingman). Wingman and the pilot are not crew layers, so the two crew layers are the lead and its workers; a lead does not spawn further leads.

**Ownership falls out of who spawns.** Every crew record carries a `parent` field, stamped by `bin/spawn-crew` from the spawner's `$WINGMAN_CREW_ID`. Wingman has none (it is the top orchestrator), so its spawns get `parent=""` (top level); a lead has its own id, so its spawns get `parent=<lead-id>`. No new flags - the tree is implicit in who ran the spawn.

**Each layer sees only its direct reports.** Surfacing (`needs-attention --owner`), the watcher, and the default `crew-list` are all scoped to an owner (`""` = top level). Wingman's watcher runs `--owner ""` and sees only the top level (including a lead's rolled-up line); a lead's watcher runs `--owner <lead-id>` (the default from its own `$WINGMAN_CREW_ID`) and sees only its own workers. The pidfile/beacon/wake are keyed by owner (`watch-<owner>.*`, `wake-<owner>`; wingman keeps the legacy unsuffixed names), so wingman's watcher and each lead's watcher coexist without contending. Drill-down is always available: `crew-list --owner <id>`, `crew-list --tree`, and the tree-rendered `board.md`.

**Escalation is recursive human-in-the-loop.** A worker that sets `blocked` surfaces to its owner (its lead), not to the pilot. The lead answers via `crew-say` if it can; if the decision is above its pay grade, it re-raises `blocked` on its *own* line, which surfaces one level up. Decisions travel up only as far as needed; the answer flows back down the same chain. Cascade stand-down mirrors this: standing down (or reaping) a member recurses to its descendants, so finishing a lead never orphans its sub-crew.

A lead's own `blocked` is reserved for the case where it has nothing left it can progress
across its whole team, not merely because one worker's task needs a decision (issue #203):
a genuinely blocking question on one unit is recorded as a `parked` annotation (`crew-set
--park`/`--unpark`, independent of `status`) while the lead keeps dispatching and
supervising everything else, escalating only once every remaining unit is exhausted - as
one batched `blocked` call that folds every parked item into `blocker` automatically, not
one escalation per question. `bin/crew-list --parked` and the `/blocked`/`/status` skills
surface these annotations alongside true `blocked` records, so the pilot's visibility into
pending decisions never depends on the whole effort looking unhealthy.

**Peers collaborate directly.** Siblings under the same lead `crew-say` each other for routine coordination (a developer↔reviewer exchange, a developer↔developer interface negotiation) without routing through the lead - which would pour their detail into the lead's context, the exact bloat the hierarchy prevents. The lead sees only the rolled-up outcome unless a genuine decision escalates. A guardrail in `crew-say` keeps collaboration within a team: a caller may message its own reports, a sibling under the same lead, or its own lead - not arbitrary crew elsewhere in the tree (override with `--force`).

**Depth cap: two crew layers.** The full chain is pilot → wingman → lead → worker; wingman and the pilot are not crew layers, so the two crew layers are the lead and its workers. A lead does not spawn further leads; deeper nesting is a future opt-in gated behind cost guardrails.

**Domain generality.** The tree, escalation, rollup, and owner-scoping know nothing about software; only the playbooks carry domain (see [playbooks.md](playbooks.md)). The playbook library ships this as a first-class taxonomy rather than a hypothetical: category subdirectories under `playbooks/` (`ai-research`, `data-science`, `scientific-research`, `business-development`, `business-operations`, alongside `software-development`) each carry a domain-appropriate pipeline, so a science lab (experimental-designer → experimentalist → analysis-scientist → peer-reviewer) or a business team (market-analyst → gtm-strategist → partnerships-rep) runs the same machinery out of the box. Adding a further domain is still a playbook swap, not a code change: reuse the default role names with domain-appropriate `*.local.md` prose, or add named roles (`playbooks/<category>/pi.md`, …) and a `lead.local.md` that sequences them. The lead playbook is written in role-and-handoff terms ("gather requirements → design → execute → review → integrate") with software as the concrete default.

## Survival & reconciliation

The tmux **server** owns the crew windows, so killing wingman does not kill the crew.
Every session and window target is exact-match (`-t "=name"`; tmux otherwise resolves bare names by prefix, which is how crew once landed inside a similarly-named session - issue #39), and `bin/spawn-crew` guarantees the crew session itself exists before creating a window in it.
On any startup wingman reads `~/.wingman/crew.json`, reconciles against the live windows (`bin/crew-list` does this automatically), re-arms the watcher if crew are in flight, and reports the current roster.
Before judging liveness, reconcile callers adopt strays: a roster member's window found in another tmux session is moved back into the crew session (`tmux move-window`, process intact), so a live member is never reported `died` merely for sitting in an unexpected session (issue #44).
A crew member whose window died shows as `died` and is recoverable either by hand (`bin/crew-takeover <id>` prints the exact resume command) or in bulk via `bin/crew-resume <id>...` / `bin/crew-resume --all-died`, which relaunches it (or every died member) with `claude --resume <session-id>` and verifies the relaunch actually took before flipping it back to `working`. Resumability itself is computed fresh at render time, not cached at the death flip (issue #251): `is_resumable()` checks whether the member's own session transcript still exists on disk (derived from `repo` + `session_id`, resolved the same way the CLI derives its own project directory - honoring a relocated `$CLAUDE_CONFIG_DIR`, with a `session_id`-keyed glob fallback for a naming scheme this derivation doesn't yet know about) - a `died` member with an intact transcript renders as `died (resumable)` in `crew-list`/`board.md`, and `crew-takeover`/`needs-attention` lead with recovery rather than reading as a dead end, still offering the resume command with an honest caveat even when the check comes back negative. The death flip itself (`cmd_reconcile`), separately, checks whether the member's worktree (if it still has one) is dirty - tracked, staged, or untracked - in which case a snapshot commit built through a scratch git index is pointed at by `refs/wip/<id>` without touching the working tree, the real index, or `HEAD`, so a death mid-edit is never one `rm -rf` away from losing that work; a genuine anchor failure (most commonly a stale `.git/index.lock` left by the crash itself) is recorded and surfaced rather than reading identically to a clean tree.
`bin/spawn-crew` itself only ever reports success once the `crew-add` write is confirmed readable back (a captured exit-status check plus a `crew-get` read-back; either failure tears the just-created window down and dies loudly) - a live, untracked session with no roster record is the failure mode this closes (issue #79).
As a backstop for the remaining ways a record can still go missing (a crash between window creation and `crew-add`, or a window created outside `bin/spawn-crew` entirely), wingman's own reconcile pass (`--owner ""` only) also tracks any live `wm-*`-prefixed window with no matching roster record in `orphan-candidates.json`, and adopts it as a `blocked` roster-only record once it has stayed unmatched past `--grace-seconds` (default 15s) - long enough that an ordinary in-flight spawn, whose window always exists a moment before its `crew-add` lands, is never mistaken for a genuine orphan.

**Every session-creation path reconciles its user-scope guard hooks before the session starts.** There are exactly three: `bin/wingman` (the top-level pilot session), `bin/spawn-crew` (every new crew session), and `bin/crew-resume` (every resumed one, which writes its own launcher and opens its own tmux window rather than going through `bin/spawn-crew`). Each runs `bin/lib/sync-user-hooks.py` against `bin/lib/user-hooks.json` immediately beforehand and refuses to start the session (fail-closed, no override) if it cannot - Claude Code binds hooks at session start, so this is the only point where writing `settings.json` still takes effect for the session about to launch. See [guards.md](guards.md#hooks-that-need-user-level-settings) for what the manifest covers and why (issue #241).

**Everything above assumes the tmux server itself stays up - which is not guaranteed.** Twice (issue #218), the shared tmux server's whole cgroup scope has been torn down with zero preceding journal trace, taking wingman-main and every crew window down with it in the same instant, since they are all just sessions on one shared server socket. Nothing that lives inside that server can be the safety net for its own death, so `bin/wingman` also launches `bin/lib/tmux-guardian.sh` on every startup, scope-wrapped independently of the tmux server it watches (the same `systemd-run --user --scope` idiom `wm_tmux_scoped` already uses, falling back to a plain detached process when systemd-run is unavailable). It polls whether any tmux server answers at all, keeps a small overwritten "last known good" heartbeat, and - the moment the tracked server pid disappears or turns over to a different pid with no observed gap - appends a bounded forensic event (the last heartbeat, a full process snapshot, and the new pid's ancestry chain walked via `/proc`) to `~/.wingman/tmux-guardian-events.log`. It fixes nothing and restarts nothing; it exists only to leave the trail issue #218's own investigation found missing, so a recurrence is diagnosable instead of another zero-trace mystery. It is not `bin/watch-fleet` and must never be run the way `bin/watch-fleet` is: watch-fleet's entire wake mechanism depends on being a harness-tracked task whose *exit* re-invokes wingman, so it must never be detached; the guardian's entire purpose is to survive the one event that kills a harness-tracked task too, so it must always be detached, and none of watch-fleet's wake-loop rules apply to it.

## Tests

`bash tests/run.sh` runs the bash E2E suites.
No real `claude`/tmux fleet is needed; each test uses an isolated throwaway state home and tmux session name.
They cover:

- the wake loop (`watch-fleet` blocks, fires on an actionable event, singleton guard, an atomic claim so two near-simultaneous arms never both win),
- terminal-event de-duplication (an event surfaces once, re-surfaces only on a state change),
- repo-vs-global spawn scope,
- roster views and cleanup (`crew-list` hides `stood-down` by default, `--all` reveals it; `crew-prune` archives + removes terminal records),
- silent-stall detection (the staleness gates, the execution probe, and the API-error reason flavor + nudge-then-escalate flow) and the bounded confirm-or-escalate self-heal nudge (`tests/stall-nudge-confirmation.test.sh`: confirmed vs. unconfirmed-and-retried delivery, marker TTL expiry, legacy-marker upgrade safety),
- nudge visibility and the long-shell duration ceiling (`nudged_at`/`long_shell_*` tracked and cleared correctly, `crew-list`/`board.md` annotating a still-`working` member without ever causing a flip) and the interactive-prompt guard's crew-vs-top-level scoping,
- correlated-event grouping (`group-attention` collapsing a mass-death or API-outage batch into one bullet) and bulk recovery (`crew-resume`, including its idempotency guards and tree preservation),
- PR-event evaluation including `checks-passed` (fires once on green / no-CI, re-arms after a new failing/pending rollup) and `merge-ready` (the same settle, firing instead of `checks-passed` when the member's crew record carries `allow_merge: true`, including when that grant lands after the PR already settled),
- confirmed-write spawning and orphan recovery (issue #79): `bin/spawn-crew` tears down its window and fails loudly on a `crew-add` failure or a failed verify-after-write read-back; `with_locked` propagates a real `flock()` failure instead of swallowing it; `wm_state reconcile` adopts an orphaned `wm-*` window as `blocked` only once it has genuinely outlasted the grace period, never a healthy in-flight spawn.
- the out-of-cgroup tmux-server guardian (issue #218): first-seen/died/revived/changed detection against a real, disposable private tmux server, idempotent startup (a second `--daemon` invocation never duplicates), `--stop`/`--status`, and the events log staying bounded across repeated death/revival cycles instead of growing without limit.

Requires `bash`, `git`, `tmux`, and `uv`.
